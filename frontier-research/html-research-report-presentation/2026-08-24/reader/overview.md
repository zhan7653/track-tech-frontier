# 结论总览：HTML 应成为理解层，而不是另一个内容源

## 先给答案

现有仓库的 Markdown 已经承担了权威内容、相对链接和审计边界。HTML 层最有价值的工作不是重写结论，而是补上三种读者能力：先看见整套报告的结构，在一页内保持位置感，并把技术关系从文字重新表达成可检查的图、表和状态。

Idyll 的论文把“可读标记语言”和“可扩展交互组件”之间的接口作为降低交互文章制作成本的核心，并在首次使用研究中观察到学生能够掌握语言概念并制作交互文章。

EMAR 的论文提出一条更严格的交互边界：交互报告应像普通正文一样可读，读者不操作控件也能学习，交互用于检查假设变化造成的后果。
<!-- claim:C010 -->

因此，本仓库的 HTML 不应该变成 dashboard，也不应该要求作者把每篇报告改写成组件代码。它应当默认完整保留原文；交互只服务于定位、比较、展开机制和检查证据。

交互只有在帮助读者定位、比较、改变有意义的假设、检查证据或重建数据流时才值得加入，并且必须保留无需交互也能读懂的退化路径。

## 读者真正面临的三个断点

### 1. 从入口到专题：不知道先读什么

当前套件有总览、架构、六个机制、四个场景、横切问题和项目报告。Markdown 链接是正确的，但目录树本身不会解释阅读顺序。HTML 首页应把“5 分钟、15 分钟、专题、工程、证据”这些路径变成显式入口，并标出每页的类型、阅读时间和上下文。

### 2. 在长页里：知道内容，却失去位置

套件级侧栏解决“我在哪个文件”；页内目录和滚动状态解决“我在这一页哪里”；专注模式允许读者暂时收起两者。三者不能互相替代。

面向多文件技术套件的导航至少需要套件层、页面层和专注阅读层：套件层呈现机制关系，页面层维持标题与段落位置，专注层允许暂时移除导航负担。

W3C 的页面结构指南指出，正确的区域、标签和层级标题能同时改善屏幕阅读器、键盘、低视力、认知障碍和移动阅读模式下的定位。
<!-- claim:C011 -->

### 3. 从文字到机制：看过了，但不能复述系统怎样运作

技术报告最难的部分通常不是术语，而是状态怎样流动、决策在哪里发生、成本和错误被转移到哪里。HTML 应优先增强已有 Mermaid、比较表和代码块：图必须有文本后备；表需要可横向阅读和行聚焦；代码应复制但不能喧宾夺主；来源应靠近结论而不是独立成一堵链接墙。

## 本仓库应采用的边界

- 保留 Markdown 为唯一内容源；HTML 是可重建产物。
- 使用构建时生成的静态页面与检索索引；页面打开后不依赖服务端。
- 不执行源 Markdown 中的原始 HTML 或脚本；链接协议需要白名单。
- Mermaid 优先在构建时转成可访问 SVG；失败时显示结构化文本和原始定义。
- 用一套设计令牌控制颜色、排版、密度、打印和深色模式，不让每篇报告自行设计。
- 搜索结果包含页标题、章节标题、摘要和命中片段，并能直接落到章节锚点。

## 不采用什么

- 不把 56 个现有页面手工改写为 React/MDX 组件。
- 不把数据 dashboard 的格栅密度当成长文默认排版。
- 不为展示效果引入需要在线 CDN 才能读懂正文的关键依赖。
- 不让折叠区吞掉核心结论；折叠只用于来源、代码、补充解释或已在正文总结过的内容。
- 不把 Star 数、模板数量或框架功能清单当成适合本仓库的证据。

## 下一步怎样落到实现

实现应分四个可浏览版本推进：先保证语义转换与链接正确；再建立阅读层级；随后增加理解组件和检索；最后完成移动、键盘、打印、深色和无脚本退化。每一版都必须在真实的 Agent Memory v10 套件上生成页面并由浏览器检查，而不是只测一段样例 Markdown。
