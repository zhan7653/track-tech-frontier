第一部分 · Conversation memory

会话历史怎样从 L0 演化到 L3

这里的四层不是四次重复摘要。它们分别保存原话、原子信息、场景方法和长期准则，粒度越来越高，使用方式也不同。

L0 · 原始对话消息

L0 到底是什么？

就是一条一条的 user 输入和 assistant 最终回复。只看这一轮真正新增了什么，不做“经验总结”。

输入

Proxy 或调用方提交本轮真实消息，同时带上 team、user、agent、session，必要时再带 task。

{
  "team_id": "team-alpha",
  "user_id": "user-alan",
  "agent_id": "coding-agent",
  "session_id": "session-001",
  "messages": [
    {"role":"user", "content":"修 bug 前先写失败测试"},
    {"role":"assistant", "content":"收到，我会先复现再修改"}
  ]
}
输出

一条消息一条记录，每条都有自己的 ID、role、content 和 timestamp。接口返回 accepted_ids，只表示 L0 接收成功，不是 L1 结果。

[
  {
    "id": "msg-a1",
    "role": "user",
    "content": "修 bug 前先写失败测试",
    "timestamp": 1785924000000
  },
  {
    "id": "msg-a2",
    "role": "assistant",
    "content": "收到，我会先复现再修改",
    "timestamp": 1785924005000
  }
]
标准 Chat Memory L0 只接受 user 和 assistant。system、tool_call、tool_result 不在这条链里；完整工具轨迹由 Skill 采集链路处理。上游还会移除已经注入过的 memory/persona/scene 块，避免旧记忆原样回灌。

L1 · 原子长期记忆

L1 做的不是摘要，而是挑出值得长期保存的独立信息

它会从若干 L0 消息中抽取事实、任务、方法或资产线索；每一条都要能够独立检索和独立更新。

01
达到触发条件

当前配置通常累计若干轮对话后运行；新 Session 还有 1→2→4→5 的 warm-up 阈值，也可以被空闲时间触发。

02
LLM 抽取候选

固定 System Prompt 定义哪些类型值得保留、证据边界和 JSON 格式；动态 Prompt 放背景消息与本轮新增消息。

03
为每条新记忆找相似旧记忆

用新 content 做向量召回；没有向量能力时用 FTS5/BM25。只取 Top-K 相似候选，不扫描整个记忆库。

04
LLM 判断冲突与重复

把“新记忆 + 相似旧候选”交给去重 Prompt，选择 store、update、merge 或 skip。

05
写入原子记忆库

保留 team/user/agent/session/task、类型、优先级、来源消息和版本信息，供后续搜索与 L2 整理。

L1 抽取 Prompt 在判断什么？System + dynamic messages
  • 只保存未来仍有价值、能够独立理解的内容。
  • code 模式偏团队事实、任务、工作方法和资产；chat 模式偏用户事实、偏好和个人经历。
  • 用户明确采纳的约定可以保留；Assistant 单方面提出、用户尚未接受的建议不能自动变成团队事实。
  • 输出必须是结构化候选，不把整段对话原封不动复制成记忆。

{

  "similarity": 0.91

去重结果

两条表达的是同一方法，新版本更具体，因此常见结果是 merge：保留旧记忆身份，把内容更新为更完整的表述，而不是再新增一条。

新 L1 并不是“自己知道”要和哪条旧 L1 比较。它先依赖检索系统找候选，再由 LLM 做语义判断。标准去重路径通常还受 session/task 约束；主动记忆召回则可以跨 session，所以“写入去重范围”和“以后搜索范围”并不完全相同。

L2 · 场景方法文档

L2 把零散记忆整理成“以后遇到这类事怎么做”

它不再是一条事实，而是一份可以不断改写的工作场景文档，里面有适用条件、步骤、判断逻辑、反模式和证据。

输入

本次新产生的 L1 内容，加上 team + agent 已有的场景索引。LLM 看到的是记忆正文和现有场景摘要，不会直接拿到 L1 的所有 metadata。

New memories:
- 修 bug 前先建立稳定失败的复现测试
- 修完后要运行相关回归测试

Existing scenes:
- scene_blocks/testing-strategy.md
- scene_blocks/release-validation.md
整理动作

Scene Agent 根据固定 Prompt 判断：

  • UPDATE：补强已有场景。
  • MERGE：合并高度重叠的场景。
  • CREATE：确实没有合适场景时新建。
  • 保持克制：避免每条 L1 都变成一个文件。
L2 是固定提示词吗？fixed policy + dynamic data

是。固定 System Prompt 定义场景的 Markdown 骨架、UPDATE/MERGE/CREATE、热度、容量和允许的文件操作；动态部分才放新 L1、旧场景索引、当前时间和容量警告。

整理完怎么用？

新 Session 不会把所有 L2 正文塞进 Prompt，只注入 path + summary 导航。Agent 判断当前任务相关时，再读取那一个 Markdown 文件。

怎么验证真的有用？

先确认新 Session 出现索引，再看 Agent 是否实际读取正文；最后在固定模型、任务和工具的条件下做有/无 L2 的 A/B，并加入无关场景负对照。

L3 · 跨场景长期准则

L3 从多个场景里提炼“长期都应该怎样工作”

如果 L2 是一本本场景手册，L3 就是这支 Agent 的团队工作准则。它不保存项目进度，而是把多个 L2 中能够跨任务复用的原则、SOP、判断标准和禁忌写进同一份 persona.md。

什么时候触发

首次生成：第一次 L2 场景整理完成、已经存在场景文件，但还没有 L3 正文时立即生成。

常规更新：上次 L3 成功后，又累计保存了 50 条新 L1。这里数的是新写入的 L1，不是 50 轮对话，也不是 50 个 L2 场景。

提前更新：L2 发现跨场景的重要规则时，可以写入 PERSONA_UPDATE_REQUEST 主动请求更新，不必等到 50 条。

恢复生成：系统记录显示以前生成过 L3，但 persona.md 正文丢失或为空时重新生成。

阈值怎样计数

每次 L1 抽取完成后，实际成功写入的 L1 数量会累加到 memories_since_last_persona。

上次 L3 生成后：0
Session A 新写入 L1：12  → 12
Session B 新写入 L1：21  → 33
Session C 新写入 L1：17  → 50
                         ↓
                   触发 L3 更新

L3 成功写入后，该计数归零，同时记录本次生成时间；下一轮从 0 重新累计。当前仓库配置和库级默认阈值都是 50。

01
确定本次输入

首次生成时，所有现有 L2 都算“变化场景”；增量更新时，只选择 updated 晚于上次 L3 生成时间的 L2，并读取这些场景的完整 Markdown。

02
组装 LLM Prompt

动态输入包含变化 L2 的完整正文、旧 L3 全文、触发原因、当前时间、累计处理消息数、L2 总数和变化 L2 数量。L3 不直接读取原始 L0，也不直接读取整批 L1 metadata。

03
比较旧规则与变化场景，重写同一份 L3

如果新场景只是再次证明旧规则，保留原句或把证据压进原句；出现新的通用方法时补充；旧规则过于绝对时改写适用条件；规则重复或过长时合并删除；只有项目状态时不更新。它不会为每批新内容机械追加一条规则。

04
写入并注入

首次生成或大改时用 write 整体写入 persona.md，小改时用 edit 精确替换。工程侧清理模型误写的导航，再追加最新 L2 场景导航；新 Session 把 L3 正文直接放进 System Prompt。

“修改旧规则”具体是什么意思？replace, not append-only

假设旧 L3 写的是：

- 所有代码修改前都必须先写失败测试。

新的“重构与行为保护”L2 说明：纯重构不一定存在待修复的失败行为，但必须先建立行为基线和回归保护。L3 不会再追加一条相互矛盾的规则，而是把旧规则改成：

- 修复行为缺陷时，先建立稳定失败的复现测试；
  纯重构时，先建立现有行为基线和回归保护，再修改实现。

如果 L3 中同时还有“修 bug 前先复现”“没有失败证据不要修改”等重复表述，则合并进上面这一条并删除重复项。这就是修正和压缩：直接改写同一份准则，使规则更准确、更短，而不是只在末尾追加。

code 模式最终正文必须控制在 1200 字以内，只保留跨工作场景可复用的内容。文件保存于 team + agent 的 Profile Scope；工程侧会在正文后追加 L2 场景导航。

输出怎样使用：新 Session 初始化时，Memory Injector 读取 persona.md，把 L3 正文直接放进 System Prompt。它不是通过向量搜索按需召回，因此每一轮都会影响 Agent 的默认判断和行为。已有 Session 通常使用 session_init 缓存，要验证刚更新的 L3，应开启新 Session。
code 模式下，L2/L3 表达团队场景和工作准则；chat 模式下，它们更接近用户生活场景和长期画像。L0 格式没有变化，但 Prompt 的保留标准和输出语义不同。当前 v3 Profile Scope 仍是 team + agent，多用户 chat 部署不能只切换 Prompt 而忽略画像隔离。

第二部分 · Skill

从“记得这件事”到“会执行这类任务”

L0–L3 主要从对话里沉淀事实、场景和原则。Skill 看的是一次真实任务怎样被执行：调用了什么工具、遇到什么失败、怎样判断、怎样验证。

Skill 不是 L4，它是一条平行的能力沉淀链

一条记忆可以说“修 bug 前要先写测试”；一个 Skill 则要写清楚什么时候使用、需要什么输入、具体怎么做、遇到分支怎样判断、最后如何验证。

Review Agent分类、评分、查重、创建或更新
版本化 SkillSKILL.md、supporting files、active head
采集输入

Proxy 等到一次真人轮次真正结束，再提交该轮完整规范化轨迹。标准采集路径实际形成四种 role：user、assistant、tool_call、tool_result。它比只收 user/assistant 的 L0 多保留了执行过程。

user: 修复登出后 refresh token 仍有效的问题
assistant: 我先定位认证链路
tool_call: 运行 auth 测试
tool_result: refresh token test failed
tool_call: 修改 token revocation store
tool_result: patch applied
tool_call: 运行测试与回归
tool_result: all passed
assistant: 已修复并验证
什么时候整理

Buffer 按 space + user + team + agent + session 隔离。当前默认达到任一条件就归档并异步 Review：

  • 累计 10 次 tool_call；或
  • 累计约 40KB 内容。

这些计数不跨 Session 相加。一次 Archive 只消费当前 Session 的一段轨迹。

为什么接口定义里还能看到第五种 system？ /v3/skill/conversation/add 的 Schema 和 Core Handler 为兼容调用方接受五种 role，但标准 Proxy 在 Anthropic、OpenAI 两条规范化路径中都会过滤 system，Review Extractor 也只识别上面的四种标记。若绕过 Proxy 直接把 system 交给当前 Core，转给 Review 时还会被降级成 user。所以“五种”是接口兼容范围，不是标准 Skill 证据的五种实际角色；正常调用不应主动提交 system。

Review Prompt 怎样决定“这次经历值不值得变成 Skill”

后台 Review Agent 不应该见到工具轨迹就机械生成 Skill。它的固定 System Prompt 把“不生成”视为正常结果，并要求先查看已有 Skill。

01
识别可复用能力

一次性修补、只对当前文件有效的信息、没有稳定判断逻辑的过程，不应创建 Skill。

02
分类并评分

先在 Skill、Memory、Wiki、CodeGraph、Temporary Context 五种归属中分类；只有归入 Skill 且达到 72 分接受门槛才继续。这里的“五种”是知识归属，不是输入 role。

03
先 list / view

Extractor 先给出同一 team + owner-agent 最近更新的最多 5 个名称和摘要作为提示；Review Agent 仍须通过 skill_list 和 skill_view 工具检查完整 Skill 库。

04
选择写动作

可以 create、update、patch 或 files_write；后台 Review 没有删除工具。

05
形成新版本

更新不会覆盖历史快照；owner 校验和 expected_version 乐观锁避免并发任务互相覆盖。

已有 Skill 到底怎样查recent hints → list → view → decide

不是把所有 SKILL.md 一次塞进 Prompt，也不是只靠向量相似度自动决定。查询分成四步：

① 最近 5 个提示

Extractor 在调用 LLM 前直接读取最近更新的最多 5 个 Skill，只把 name + description 放进动态 Prompt。它提供时间线索，不代表全集。

② skill_list

Review Agent 必须先调用读工具。不带 query 时列出现有项；带 query 时按名称和描述缩小候选，得到 ID、摘要和版本。

③ skill_view

只要某个候选可能相关，就再用读工具加载它的完整 SKILL.md 和 supporting files manifest，判断能力边界是否真的重叠。

④ 决定动作

没有相关项才 create；已经完整覆盖就 Nothing to save.；相似项缺少小块内容就 patch，需要整体改写才 update。

一个 Skill 怎样跨 Session 继续演化

Buffer 不跨 Session，但 Skill 身份和版本跨 Session。新任务的 Archive 会读取已有 Skill，用新证据修正 Workflow、Decision rules、Validation 或 Pitfalls，然后创建新版本。

Session A

第一次完成 token 撤销修复，生成 auth-token-revocation@v1。

Session B

发现多实例部署下本地撤销表不可靠，Review 读取 v1，把共享存储要求补进 Decision rules，生成 v2。

Session C

又发现回归测试必须覆盖旧 token 与并发刷新，Review 补强 Validation，生成 v3。

新会话

System Prompt 只注入 owned active Skill 目录；任务匹配时再读取 v3 的完整 SKILL.md 和 supporting files。

Skill 目录通常按 session_init 缓存，所以另一个任务刚生成的新版本不会稳定出现在已经运行中的 Session。要验证新 Skill 是否被 Agent 看见，应开启新 Session，并检查目录、读取轨迹和最终执行结果。

第三部分 · Wiki

外部文档怎样变成可搜索的知识库

Wiki 不是只保存一张关联图。真正的知识在 Markdown 页面里，Wikilink 把页面连接起来，FTS5/BM25 让 Agent 能先找到相关页。

生成从上传文档和一次显式 ingest 开始

上传 .md 或 .txt 只是保存 raw 文件。调用 ingest 后，MemoryKnowledge 才异步分析原文、生成页面并重建索引。

01
登记 source 与 SHA

先比较内容哈希；只有新增、发生变化或上次未成功的 source 才进入本轮 LLM 加工。

02
分析 Prompt 制定抽取计划

输入 Wiki purpose、extraction schema、已有页面清单和本段原文，判断应该创建或更新哪些页面。

03
生成 Prompt 输出 FILE 块

模型输出文件路径和完整 Markdown；页面应有独立含义、sources、摘要和必要的 Wikilink。

04
工程层规范化与合并

校验 canonical path、保护 locked 页面、合并 sources、限制结构文件，避免模型随意写目录。

05
重建全文索引与关系边

最终 Markdown 写入 FTS5/page_meta；从 [[Wikilink]] 提取 graph_edge。

Wiki 的两阶段 Promptanalyze → generate

分析阶段让模型先理解 purpose/schema、原文和已有页面，给出抽取计划；生成阶段再按 FILE 协议输出页面。这样可以先判断页面边界，再写正文，而不是把每个 chunk 直接变成一页。

## Wiki Purpose
这个知识库要服务什么问题

## Extraction Schema
应抽取哪些实体、概念、决策和关系

## Existing wiki pages
当前已有页面及摘要

## Source Document
本轮原始文档内容

---FILE: wiki/concepts/jwt-authentication.md---
# JWT Authentication
...
---END FILE---

生成后，页面、全文索引和关系图同时存在

页面正文 
wiki/
├── entities/api-gateway.md
├── concepts/jwt-authentication.md
├── decisions/token-revocation.md
└── overview.md

每一页有完整 Markdown 内容，Agent 最终回答所需的设计细节来自这里。

索引与关系 
title + body → FTS5 / BM25

[[api-gateway]]
      │ uses
      ▼
[[jwt-authentication]]
      │ constrained by
      ▼
[[token-revocation]]

全文索引解决“先找到哪一页”，图解决“页面之间怎样关联”。

Agent 搜索 Wiki，明确是通过工具完成的

新 Session 不会获得所有 Wiki 正文。Knowledge Injector 只放入已绑定 Wiki 的名称、ID、摘要、服务地址和统一工具说明。

看到资源

System Prompt 中出现一个 <knowledge type="wiki" ... /> 目录项。

发现工具

Agent 调用 POST /v3/tools/list，取得 search、read_page、get_graph 等真实工具名和参数。

搜索页面

调用 /v3/tools/call 的 search，用关键词召回 title、snippet、related 和 links。

读取正文

根据命中结果调用 read_page，只取当前问题所需的少数页面。

search 
{
  "knowledge_id": "wiki-auth-001",
  "tool_name": "search",
  "params": {
    "query": "JWT 登录架构",
    "limit": 5
  }
}
read_page 
{
  "knowledge_id": "wiki-auth-001",
  "tool_name": "read_page",
  "params": {
    "refs": [
      "wiki/concepts/jwt-authentication.md"
    ]
  }
}
标准 Agent Wiki search 默认是 hop=0 的 FTS5/BM25，不会自动沿图扩展召回。它会把命中页面的 related 和本批 links 一起返回；只有直接调用支持 hop 参数的数据 API，才会先找 BM25 种子，再沿 Wikilink 做多跳扩展。因此“Wiki 有图”不等于“Agent 平时默认用图搜索”。

第四部分 · CodeGraph

代码仓库怎样变成可查询的结构地图

Wiki 的页面由 LLM 整理；CodeGraph 不一样。它克隆真实仓库，解析文件、符号和调用关系，再把这些结果做成预建索引。

CodeGraph 的生成不使用 LLM

创建资源时提供 repo_url、branch 和租户/团队身份，后台经历 pending、cloning、indexing，最后进入 ready 或 failed。

Create仓库地址、分支、名称、team/service
Clone拉取指定分支并记录 commit
Index解析文件、符号、定义和调用边
Ready保存 files、nodes、edges 与同步状态
输入 
{
  "team_id": "team-alpha",
  "repo_url": "https://example.com/acme/payments.git",
  "branch": "main",
  "repo_name": "payments"
}
结果 
{
  "code_graph_id": "cg-payments-main",
  "status": "ready",
  "commit_hash": "8c4a1d9",
  "stats": {
    "files": 312,
    "nodes": 4860,
    "edges": 9174
  }
}
首次创建使用 CodeGraph init 并全量索引；已有索引可以 open + indexAll；后续 sync 只处理变化文件。手工同步和 Auto Sync Scheduler 都能让索引追随仓库。启用构建完成回调时，资源摘要按仓库名、分支和统计模板生成，也不调用 LLM。

它没有“生成 Prompt”，但有“怎样使用工具”的运行时 Prompt

Knowledge Injector 会告诉 Agent：先把 CodeGraph 当作地图，按问题选择工具；整张图和全部源码不会直接塞进 System Prompt。

explore理解某个功能怎样工作，按文件返回相关符号的完整源码；通常是首选。
search按名称或类型找符号位置，不返回完整源码。
callers沿调用边查谁调用了某个符号。
callees沿调用边查某个符号又调用了谁。
impact按 depth 查修改一个符号可能影响哪些依赖方。
node读取单个符号的定义、关系和可选完整源码。
files一次性查看项目目录与语言/符号统计。
status查看索引文件、节点和边的健康状态。
运行时工具选择 Prompt 的核心意思knowledge tools
  • 理解功能或调用流程，先用 explore。
  • 只找定义位置，用 search；只看一个符号，用 node。
  • 查上下游，用 callers/callees；重构前评估影响，用 impact。
  • 先调用 tools/list 取得真实工具 schema，再通过 tools/call 执行。
  • 索引明显落后，或即将实际修改代码时，再以工作区最新源码作最终确认。

“CodeGraph 是图搜索吗”要看具体调用

底层确实保存文件、符号和关系边，但每个工具的查询语义不同。

不是图遍历的部分

search 主要做符号名与类型匹配，用来找到节点；不能把它直接说成多跳图搜索。

明确查询关系图的部分

callers、callees 沿调用边查询，impact 按深度遍历依赖关系。

和 Wiki 一样，Agent 先在 System Prompt 中看到已绑定 CodeGraph 资源，再通过 tools/list → tools/call 主动查询。CodeGraph 的“演化”来自仓库 commit 变化与索引同步，不是从一次对话反馈中自动改写代码关系。

把四条链交回 Agent

内容生成以后，怎样真正进入下一次任务

资产存在不代表 Agent 已经能用。中间还要经过登记、权限、绑定和不同的注入方式。

Asset 是登记卡，Loadout 是当前 Session 的实际装配结果

Chat Memory、Skill、Wiki 和 CodeGraph 的真实内容仍保存在各自系统里。Asset 只统一登记 ID、类型、所有者、版本、可见性、状态和 content_ref。

登记

meta_assets 记录资产是什么、属于谁、状态如何、真实内容在哪里。

授权

private、team、restricted 与 ACL 决定哪些用户或 Agent 有权使用。

绑定

meta_agent_fixed_assets 记录哪个 Agent 固定携带哪些资产。

过滤

Session 初始化时结合身份、能力开关和状态，跳过不可见或 archived/deprecated/failed 的资产。

装配

Memory、Skill、Knowledge 各自的 Injector 把内容编译成全文、目录或工具说明。

Memory

L3 全文直接注入；L2 只放索引；L0/L1 通过记忆工具按需查。

Skill

Session 初始化时先依据 Agent/Task 描述预筛 owned active Skill 目录；当前任务命中后，主 Agent 再读取 SKILL.md 和 supporting files。

Wiki / CodeGraph

只注入资源目录和 tools/list、tools/call 说明，正文或关系由工具按需返回。

仓库目前没有独立的 LoadoutEntity 或统一 token-budget 编译器。injection_mode 和 priority 已经存储，但运行时仍主要按资产类型走各自 Injector；Skill 还有自身 owner_agent_id 路径。多数目录按 session_init 缓存，因此绑定、状态或版本变化后，应开新 Session 验证。

不是同一套查询路由，也不是只有一层判断

代码先决定当前 Agent 有权看见什么、哪些内容直接放进 Prompt；同一个主 Agent 再根据当前问题选择零个、一个或多个资产；最后才进入各自不同的查询通道。仓库里没有一个统一的 asset_router 替模型做四选一。

01
控制面先筛资产

固定绑定（Skill 另有 owner-agent 目录路径）、ACL、状态、能力开关和当前身份，先决定哪些 Memory、Skill、Wiki、CodeGraph 可以进入本 Session。

02
各自 Injector 分别装配

Memory、Skill、Knowledge 并不先汇入一个通用检索器，而是分别生成全文、索引、目录和工具说明。

03
一部分内容直接生效

L3 全文已经在 System Prompt 中，无需查询；L2 场景索引、Skill 目录、Wiki/CodeGraph 资源目录只提供下一步导航。

04
主 Agent 做跨资产判断

它根据“历史、流程、设计、代码实现”等意图决定是否读取；这不是互斥选择，同一任务可以组合多种资产。

05
进入不同后端

Memory 走 memory-bridge，Skill 走 skill-bridge，只有 Wiki 与 CodeGraph 共用 Knowledge 的 tools/list → tools/call 外层协议。

Chat Memory

L3 不查：全文在新 Session 直接影响推理。L2 先看索引：匹配场景时用 tdai_read_scene 读取正文。L0/L1 主动查：当前生产注册已下线逐轮自动 L1 召回，涉及历史原文、偏好或约定时，由 Agent 调 tdai_conversation_search 或 tdai_memory_search。

/memory-bridge/v3/atomic/search
/memory-bridge/v3/conversation/search
/memory-bridge/v3/scenario/read
Skill

代码先预筛：Session 初始化用 Agent 描述、Prompt、Task 描述和目标形成查询，生成当前 Agent 的 <available_skills>。Agent 再选：当前任务匹配 name/description 时调用 skill_view；目录不足时才用 skill_search 查团队可见 Skill。

/skill-bridge/v3/skill/search
/skill-bridge/v3/skill/get
/skill-bridge/v3/skill/files/read
Wiki

代码只注入已绑定 Wiki 的名称、摘要、ID 和服务地址，不会按本轮问题自动搜正文。Agent 遇到设计背景、概念、约束或历史决策时，通过统一 Knowledge 工具先 search，命中后再 read_page。

/v3/tools/list
→ /v3/tools/call: search
→ /v3/tools/call: read_page
CodeGraph

它与 Wiki 共用资源目录和 tools/list、tools/call 外层协议，但查询引擎不同。Agent 遇到符号位置、实现流程、调用上下游或改动影响时，选择 explore、search、callers/callees 或 impact。

/v3/tools/list
→ /v3/tools/call: explore
→ callers / callees / impact
同一个任务可以组合四种资产not a four-way switch

例如用户说：“按我们上次的约定修复 refresh token 撤销问题，先解释设计原因，再确认改动影响。”主 Agent 可以把一句话拆成四种信息需要：

上次约定

查 Chat Memory 的 L0/L1；如果已经写在 L3，则直接使用。

怎样修复与验证

从 Skill 目录匹配缺陷修复或 Token 撤销流程，并读取正文。

为什么这样设计

搜索 Wiki，再读取命中的设计页面。

代码在哪里、影响谁

用 CodeGraph explore 定位实现，再用 impact 查看关系范围。

当前的“跨资产路由”本质上是分散在多个 Prompt 块中的使用规则，最终由同一个主 LLM 综合执行；代码没有独立分类模型、统一状态机或全局优先级算法来保证它一定选对、避免重复查询。各资产也不是竞争一个唯一答案，而是可以在同一轮互相补充。

整体总结

这套系统怎样形成自进化

模型权重没有改变。改变的是外部资产的内容、版本、索引和下一次调用时可见的上下文。

四种输入，各自形成一条更新链

会话

L0 记录真实消息，L1 去重并保留原子记忆，L2 改写场景，L3 提炼长期准则。

执行

Skill Review 从真实任务轨迹中提炼能力，并用新 Session 证据持续创建版本。

文档

Wiki 用 source SHA 找变化，LLM 生成或合并页面，再重建全文索引和关系图。

代码

CodeGraph 随仓库变化重新解析文件、符号和调用边，让查询结果追随真实代码。

复用

Asset、ACL 和 fixed binding 选中资产；Injector 在新 Session 中注入全文、目录或工具协议。

新证据

Agent 按这些经验完成下一次任务，新的对话、轨迹、文档和 commit 再进入各自更新链。

效果反馈和人工选择做到哪里了

仓库已有一些反馈与治理基础，但“使用后自动判断资产好坏”还没有形成完整闭环。

Asset Reflection

默认关闭。开启 opt-in 且请求路径包含 /analyse 时，Prompt 会让 Agent 在最终回答末尾写：

【资产反思】
- <tag>::<tool_name>：
  这次是否有用，得到什么，或为何没命中

当前没有自动解析这段文字，也不会据此回写 Asset、调整排名或改写内容。

人工选择

人可以用 visibility/ACL、bind/unbind、状态和版本控制哪些经验能够存活和传播。

  • Skill 更新保留不可变版本。
  • Fork 会复制内容，之后两份独立演化。
  • runtime 会过滤 archived/deprecated/failed。
  • draft/candidate/approved 目前更像治理标签，并非完整强制发布闸门。

已经闭合的部分

  • 新证据可以生成或更新 Memory、Skill、Wiki、CodeGraph。
  • 重复内容有去重、合并、版本或增量同步机制。
  • 被选择的资产能够在新 Session 中重新交给 Agent。
  • 人能够控制共享、绑定、Fork、废弃和权限。

还缺少的部分

  • 稳定记录资产是否真的被调用和命中。
  • 把一次资产使用归因到最终任务质量。
  • 根据效果自动评分并调整检索或 Loadout 排名。
  • 受治理约束地自动强化、改写、降级或淘汰资产。

怎样证明一次“进化”真的产生了效果

01
先看资产是否变化

检查 L1/L2/L3 内容、Skill version、Wiki 页面/索引或 CodeGraph commit/stats。

02
再看是否进入新 Session

核对 Asset、ACL、binding 和最终 System Prompt，避免把“已经生成”误当成“已经装配”。

03
确认是否真的使用

查看 L2/Skill 读取轨迹，或 Wiki/CodeGraph 的真实工具调用，而不是只看目录出现。

04
最后比较任务结果

固定模型、温度、任务、代码和工具权限，比较有/无资产时的成功率、步骤数、token、错误和返工。

05
加入无关资产负对照

确认 Agent 不会因为目录里有内容就盲目读取或套用，才能证明检索和选择是有效的。

这套仓库已经实现了“新证据 → 外部资产持续更新 → 被选择的资产回到下一次 Agent”这条主干。它当前最准确的定位，是自动沉淀与复用经验、由人控制传播；下一步真正需要补齐的，是以任务结果为依据的自动归因、评分和资产优化。
