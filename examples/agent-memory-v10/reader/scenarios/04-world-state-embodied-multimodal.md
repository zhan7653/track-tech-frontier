# 世界状态、具身与多模态 Memory：记住的不是图像，而是可行动的“现在”

具身或多模态 Agent 面对的是不断变化、又只能部分观察到的世界。它的 Memory 不能只把图像转成文字再做向量检索；还要保存某个观察在何时何地发生、当时看得见什么、它如何改变对世界的判断，以及后续动作是否证实或推翻了这个判断。

## 这个场景保存什么

| 对象 | 内容 | 为什么需要独立管理 |
|---|---|---|
| 原始观测与轨迹 | 图像、文本、传感器输入、动作与环境反馈 | 作为可回溯证据，保留时间、可见性和来源 |
| 世界状态 | 实体、关系、位置、状态及其历史版本 | 回答“现在是什么”与“此前何时改变” |
| 经验与技能 | 具体动作经验、可迁移的任务程序 | 回答“如何做”，不能覆盖“当前世界是什么” |
| 个性化语义 | 用户偏好、视觉概念和个体互动历史 | 只在长期人机交互中与世界状态并行出现 |
| 预算化上下文 | 为本轮规划压缩出的子图、轨迹和技能片段 | 控制输入预算，但不能变成唯一事实来源 |

这一区分很重要：如果把“门已打开”与“如何开门”的技能放进同一种、无版本的文本 Memory，系统很难知道哪一句已经过时，也难以定位失败来自观测、状态更新、检索还是规划。

## 场景组合：write → manage → read → use 的观测到行动闭环

```text
视觉 / 文本 / 环境信号
             │
   归一化：时间、空间、可见性、来源、动作前后关系
             │
 ┌───────────┼────────────┬───────────────┐
 │           │            │               │
原始轨迹   世界状态图   动作经验→技能   个性语义/视觉概念
 │           │            │               │
 └───────────┴──────┬─────┴───────────────┘
                     │
 当前目标 ──> 时效/冲突处理 ─> 子图、轨迹与技能检索 ─> 预算压缩
                                                               │
                                                           规划与行动
                                                               │
                                               新观察、成败和状态校验回写
```

这个闭环将“Memory 正确”拆成五个问题：是否正确建档观察；是否把它更新为恰当的当前/历史状态；是否抽取了可迁移经验；是否为当前目标取到适当内容；以及规划是否真的按新状态行动。最终任务失败可能出在任一段，不能只从问答准确率判断。

## 主流方案形状与它们解决的瓶颈

| 方案形状 | 组合重点 | 代表工作 | 主要限制 |
|---|---|---|---|
| 世界状态图 | 将情节与语义世界模型连接，随探索更新 | [AriGraph](https://arxiv.org/abs/2407.04363) | 部分可观测、旧状态覆盖，以及图到计划的转换仍困难 |
| 轨迹—技能双流 | 累积视觉落地经验，再抽取任务级技能并按情境适配 | [XSkill](https://arxiv.org/abs/2603.12056) | 技能迁移不应掩盖具体状态与前置条件 |
| 个性化多模态图 | 将用户语义/视觉概念与具身轨迹分开 | [POLAR](https://arxiv.org/abs/2605.26256) | 身份漂移、纠正、删除和长期真实用户效果未闭合 |
| 固定预算压缩 | 在有限 token 下把长轨迹压成规划可读的状态 | [MeMento / DunphyBench](https://arxiv.org/abs/2608.01456) | 压缩可能丢失来源、冲突和仍与任务相关的细节 |

这些形状可以相互连接，却不构成可互换的排行榜。图侧重显式关系和当前状态；双流侧重从经验到技能的复用；个性化图把用户状态从环境状态中分离；压缩解决的是读取预算。现有材料尚未在相同环境、规划器、token 和动作预算下证明其中一种在所有任务上更好。

## 当前证据怎样改变了问题表述

[WorldLines](https://arxiv.org/abs/2606.18847) 将长时具身状态的困难集中为部分可观测、状态被覆盖以及从 Memory 到规划的转换；[STALE](https://arxiv.org/abs/2605.06527) 的冲突场景则表明，存储已更新并不保证行为使用了新前提。两者共同提醒：检索到正确历史不是终点，行动前的状态解释和执行后校验同样属于 Memory 闭环。

在固定预算压缩上，MeMento 的作者在 DunphyBench 对照中报告，相对其最强基线准确率提高 7.18%、memory usage 降低 85.38%。这个数字是特定作者协议下的有力信号，不能外推为世界图维护、技能学习或真实机器人系统的通用成本结论。[论文](https://arxiv.org/abs/2608.01456)

工程证据也需要谨慎解读。JARVIS-1 的已检查发布物是离线评估快照；README 明示在线增长 Memory 的 descriptor、retrieval 与部分学习路径未发布。其依赖包括视觉/强化学习运行时、Minecraft/Malmo、JDK 与外部 API，说明具身环境的集成面远比普通 Memory SDK 更宽；但 v09 未执行该系统，不能据此判断安装成功率或性能。[v09 固定提交工程报告](../../../agent-memory-v09/bundle/projects/craftjarvis-jarvis-1.md)

## 成本、失败与未解问题

世界状态 Memory 的成本不仅是送给模型的 token。它还包括多模态观测写入、图合并与版本化、技能抽取、索引、压缩、规划器调用、环境执行，以及错误状态造成的修复和重试。只报告压缩率或 Memory 字节数，会遗漏维持“当前世界”所需的写入和校验成本。

主要失败模式包括：部分观测被错误硬化为事实；新观测覆盖了仍有价值的历史；压缩删除了后续任务所需的出处；检索正确但规划仍沿用旧状态；以及可复用技能在不满足前置条件时被错误调用。现有 benchmark 分别覆盖多模态长对话、游戏轨迹、状态更新或固定预算压缩，却不能直接合并成一个总分。

目前仍缺少长期、同环境、同规划器、同预算的比较，来回答：世界图、原始轨迹、技能层和压缩层各自贡献了什么；当用户纠正、状态冲突或环境变化时，哪个环节造成行动错误；以及真实具身部署的维护代价如何。因而该方向的基础机制已清晰、近期工作很活跃，但端到端工程成熟度和跨系统可比性仍有限。
