# 方案全景：从“套主题”到“受约束的解释协议”

## 四种方案家族

| 家族 | 代表 | 核心机制 | 对本仓库的价值 | 主要代价 |
|---|---|---|---|---|
| 科学出版系统 | Quarto、MyST | 结构化 Markdown、交叉引用、图表、书/站点构建 | 技术写作构件完整 | 工具链和语法迁移较重 |
| 文档站生成器 | MkDocs Material、Docusaurus | 层级导航、搜索、版本与主题 | 多文件定位成熟 | 对“机制解释”本身不够专门 |
| 数据/交互文章 | Observable、Idyll、Distill | 数据快照、响应式组件、参数化叙事 | 可让读者操作模型和假设 | 制作成本、运行时与退化路径更复杂 |
| Agent 报告/技能 | GPT Researcher、beautiful-article、tech-route-maker、power-work-report | 报告组件、单文件导出、图解详情、审阅循环 | 直接接近 AI 产物 | 容易变成一次性页面或重写内容源 |

## 已经成熟、可以直接吸收的机制

Quarto 原生支持 Mermaid 与 Graphviz，并在 HTML 中让图保持响应式；同一图在不同输出格式中会选择原生脚本、代码块或位图等表示。
<!-- claim:C001 -->

Material for MkDocs 的内置搜索在构建时从页面和章节生成索引，在浏览器用轻量全文引擎查询，不需要服务端，并能与离线输出结合。
<!-- claim:C003 -->

MyST 的 dropdown 使用标准 HTML `details` 元素，因而没有 JavaScript 也能工作；其默认站点同时区分跨页主侧栏和由标题自动生成的页内侧栏。
<!-- claim:C004 -->

Distill 把悬停引用、脚注、正文/宽图/边注布局和交互组件组织成文章协议，使证据说明靠近阅读位置而不必打断主线。
<!-- claim:C012 -->

这些机制共同指向“渐进增强”：先有语义结构，再加交互；先保证正文，再提供更快的定位和更丰富的图解。

## 需要带着边界吸收的机制

Observable Framework 用构建时静态索引提供前缀和模糊搜索，但官方文档明确说明动态数据与图表内容不会进入该索引。
<!-- claim:C005 -->

这提醒本仓库：图解节点和表格标题若只在运行时出现，就可能从搜索和无障碍树中消失。构建时应同时生成文本摘要。

`tech-route-maker` 的 HTML 把结构化 route JSON、SVG 节点和右侧详情/证据面板绑定起来，点击节点可检查说明与来源。
<!-- claim:C007 -->

这一模式适合“机制图”，但不适合把所有正文都塞进节点。正文解释、图上关系和证据详情应各自承担不同的阅读任务。

ReActicle 提出受约束语义组件、主题令牌和自包含单文件输出；截至本次观察该仓库很新、提交历史很短，且 GitHub API 未识别出仓库许可证，因此它是设计弱信号而不是可直接复制的实现基线。
<!-- claim:C008 -->

## 一个重要反例

许多研究 Agent 的“展示”只是把 Markdown 放进一个滚动卡片，并在另一个卡片列出来源。这样能交付结果，却没有为多文件导航、机制重建和证据就近阅读建立新结构。它说明“有前端”不等于“报告可理解”。

## 本仓库的组合边界

1. 从 Quarto/MyST 借结构化技术写作、图解和交叉定位。
2. 从 MkDocs/Observable 借构建时导航与静态搜索。
3. 从 Distill/Idyll 借“交互必须帮助解释”的文章观。
4. 从 tech-route-maker 借“图 + 详情 + 证据”的多层表达。
5. 从 ReActicle/beautiful-article 借语义组件和主题契约，但不引入 React 重写。
6. 从 GPT Researcher 的代码反向确认安全边界：生成内容进入 HTML 前必须净化。

结构化技术写作、静态导航检索和证据化图解可以在不改变 Markdown 权威源的前提下组合；数据应用式自由交互只有在报告存在可操作变量时才有额外收益。
