开场 · 先建立坐标

先记住一句话：Memory 不是一个库，而是一条生命周期

读者最容易把“写入、存储、检索、技能”混成一个产品名词。六层的作用，是把每一次状态变化放回它真正发生的位置。

“过去做过什么”只有经过形成、管理和上下文装配，才会在下一次任务里成为可用的经验。

讲解时抓住这一句

不要先问“用不用向量库”。先问：输入是什么、谁决定写入、哪个状态是权威、旧结论如何更新、读到的内容怎样进入上下文、结果是否真的回流。数据库只是第三层的一部分。

贯穿例子 · 同一条规则

一条“先验证再修改”的规则，怎样走完六层

用同一个例子贯穿，读者会看到六层不是六份摘要，而是同一状态在不同阶段的不同形态。

1
输入

用户要求修 bug 前先建立失败证据；工具返回测试失败。

2
形成

TencentDB 生成 L1；Codex Phase 1 生成 rollout candidate。

3
状态

L2/Persona 或 MEMORY.md 保存可读规则，原始轨迹仍可回查。

4
修订

纯重构的新证据把绝对规则收窄为条件规则。

5
读取

新任务先看摘要/Persona，再按需打开场景、手册或原始证据。

6
反馈

测试结果、引用或多路径 outcome 影响下一版 Skill/策略。

讲解顺序：每到一层，都问一次“这一层的输入是什么、处理中发生什么、输出交给谁”。读者就不会把 L1、L2、MEMORY.md 和 Skill 当成同一种对象。

01 · 输入

先把“发生过什么”保留下来

共同主干是交互—执行轨迹，但不同系统的输入通道不同。第一层不判断长期价值，只保存后续形成需要的证据与定位。

LAYER 01 · RAW MATERIAL

同一句话、一个工具调用和一个工具结果，证据强度并不一样

输入

交互—执行事件

user input、assistant response、tool call、tool result，以及 user/team/thread/task/time/cwd/branch/commit 等定位。

区分

保留角色差异

回复可能只是建议；调用只证明尝试；工具结果才是环境观察或执行结果。

输出

可回查的事件集合

进入 L0、Skill Buffer、rollout、Wiki source 或 CodeGraph snapshot，交给第 2 层。

TencentDB：四条输入链

固定提交 0aff21a 把不同对象分开接收。

  • Chat L0：user/assistant 消息。
  • Skill：完整 user/assistant/tool_call/tool_result 轨迹。
  • Wiki：上传 Markdown/text、purpose、schema、source SHA。
  • CodeGraph：repo URL、branch，随后固定到 commit。

Codex：Thread / rollout 与项目条件

固定提交 c9b19deb 将历史事件写进 rollout JSONL，Thread DB 保存 source、rollout_path、cwd、branch、commit 和 memory_mode。

user → assistant → tool call → tool result
             + cwd / branch / commit / time

视觉观察

XSkill把图片、局部视觉状态、工具调用与 outcome 放在同一轨迹。

世界/设备状态

WorldLines同时记录 dialogue、action、execution feedback 和 object/device state change。

Computer Use 事件流

Computer History捕获 click、typing、shortcut、app switch 与 accessibility context，形成可回顾摘要。

讲解时抓住这一句

输入层不是“把所有日志都存起来”，而是保留能解释意图、动作、结果和项目条件的事件。后面所有抽取、冲突和迁移能力，都受这一层是否丢证据影响。

02 · 写入与形成

从原始经历到“值得以后再用”的对象

这层决定保存什么、写成什么粒度、什么时候 no-op，以及模型输出能否通过来源准入。

LAYER 02 · FORMATION

TencentDB 把 Chat 做成 L0 → L1 → L2 → L3，把执行轨迹做成 Skill

Chat Memory

L0 原始消息
  ↓ L1：抽取未来有价值的原子记忆
  ↓ L2：整理为场景方法 Markdown
  ↓ L3：提炼跨场景 Persona 准则

Prompt 强调未来价值、独立可理解、用户采纳证据与结构化输出。

Skill Memory

完整 Session 轨迹
  ↓ Review：分类 / 评分 / 查重
  ↓ create / update / patch / no-op
  ↓ SKILL.md + supporting files + version head

先 list/view 已有 Skill，再以 expected_version 形成新版本。

贯穿示例
L0  用户：修 bug 前先写能稳定失败的复现测试
↓
L1  work_method：修复行为缺陷前先建立失败证据
↓
L2  缺陷修复与回归验证.md
↓
L3  修复缺陷先失败测试；纯重构先行为基线

Codex Phase 1

逐条合格 rollout 经过过滤、脱敏、预算控制和高信号判断，输出严格三字段 JSON：rollout_summary、rollout_slug、raw_memory，或三个字段全空的 no-op。结果先进入 stage1_outputs，不是直接可检索的长期 Memory。

Codex Phase 2

选择候选，物化 raw_memories.md 与 rollout summaries，对比旧 Memory 工作区和 Git diff，再由受限 Consolidation Agent 更新 MEMORY.md、memory_summary.md 与 skills。

MemTxn 桥接：模型先提出 write proposal，再用 source span/tool receipt 做 Ordered PatchTest；supported 才 admission/commit，unsupported reject。版本冲突和恢复留在第 4 层。
TencentDB L1 writerCodex Phase 1Codex Phase 2MemTxn
讲解时抓住这一句

“候选”不是“真相”。TencentDB 的 L1 已经是可独立检索对象，Codex Phase 1 仍只是候选；这个差异会直接决定第三层存什么、第五层能不能读到。

03 · 状态、存储与索引

正文、历史、当前视图和索引要分开

第三层不发明“更神奇的数据库”；它说明哪个载体是权威、哪个是历史、哪个只是为了查找而生成的投影。

同一条 L1 的三种形态

JSONL 继续保留历史与来源；DB current row 表达应用当前视图；FTS/vector 负责快速定位。更新时 current/index 切换，历史不等于当前可见。

records/YYYY-MM-DD.jsonl  ← history
l1_records                 ← current
l1_fts / l1_vec             ← projection

Codex 的渐进来源链

短摘要不是完整手册，candidate DB 也不是读取库。新 Thread 可以从摘要逐层回到手册、rollout summary，再沿 rollout_path 读原始 JSONL。

memory_summary.md
  → MEMORY.md
  → rollout_summaries/
  → rollout JSONL
双时间版本图 · stable identity ≠ 一条可覆盖的 row
讲解时抓住这一句

“索引能找到”不等于“正文是当前的”；“当前正文正确”也不等于“旧版本消失”。双时间版本图把现实时间和系统认知时间分开，给第 4 层的冲突管理提供状态基础。

04 · 管理与演化

先看已有系统怎样更新，再看前沿怎样把它变成状态语义

管理层的主线是 update、merge、supersede、version 和 conflict。语义遗忘不是简单删一行，而是两个固定系统都没有闭合的前沿问题。

LAYER 04 · CHANGE THE EXISTING STATE

TencentDB：显式对象与版本 head

  • L1：相似旧项 → store/update/merge/skip。
  • L2：Scene UPDATE/MERGE/CREATE/NO-OP；备份后改写，重建索引。
  • L3：变化 Scene + old Persona → 收窄、合并或移除规则。
  • Skill：expected_version → 新 immutable version → active head。

Codex：全局文件级 current state

  • 新增/变化候选 + old files + workspace diff → Phase 2。
  • 删除只由某来源支撑的局部结论；仍有其他来源则保留并修正。
  • Git baseline 让下一次运行看到未提交 diff，但没有 per-fact revision graph。
  • ad-hoc note 是控制输入，不是同步 item-level mutation。
从一次纠正到当前版本

MemTxn：把提交边界移到模型外

Ordered PatchTest检查来源支持，Temporal Resolver选择 current version，durable snapshot journal 在故障后恢复完整 active map。

proposal → source check → version resolve → commit/reject → recover

GEM/MemState：管理整个 state trajectory

GEM区分普通相关边与 typed dependency/derived-from 边。上游 revision 只让真正派生的 Scene、Persona、Skill 或索引失效/重算。

revision → dependency closure → invalidate/rebuild → governed state
语义遗忘：ForgetEval / Control-Plane Placement把 supersede、release、purge 与 mutation placement 分开。当前视图删掉、检索不返回或原始 payload 清除，都不自动证明后续不会再次派生或据此行动。
讲解时抓住这一句

现有系统擅长“把当前文本改掉”，前沿研究追问“哪个版本有资格成为 current、哪些派生物必须跟着变、故障后能否恢复，以及遗忘是否真的改变未来状态”。

05 · 读取与上下文

不同 Memory，不同进入方式：直注、导航、工具检索或来源下钻

第五层不是“统一 top-k”。对每种 Memory，分别说清楚进入方式、检索方式、输出形态和上下文位置，读者就能看懂渐进式披露。

MemFlow：先做意图路由

MemFlow将 query 分到 Profile Lookup、Targeted Retrieval、Deep Reasoning，并按 tier 分配动态预算；Validator 发现证据不足时升级路径。

OpenViking / CICL：层级与行动感知

OpenViking用 URI 递归检索和 L0/L1/L2 hydration；CICL按“哪段证据会改变下一步行动”选择和压缩上下文。

讲解时抓住这一句

“工具 + Markdown”是 Agent 看到的接口形态；BM25、vector、graph 可能藏在工具后面。真正要讲清的是：谁决定查、先给摘要还是正文、结果放在稳定区还是动态区，以及为什么继续读。

06 · 反馈、经验与持续学习

前沿真正改变的，是“使用结果怎样变成下一版”

TencentDB 的轨迹 Review 和 Codex 的 citation→usage 只是短基线。下面每个案例各自解决一个不同问题：经验如何分层、Skill 如何验证、操作策略如何学习，以及 Memory design 是否也能被搜索。

LAYER 06 · LEARN FROM OUTCOMES

TencentDB · 短闭环

轨迹 → Review → create/update/patch/no-op → immutable Skill version。能沉淀和复用，但没有稳定的 outcome attribution。

Codex · 短闭环

citation → usage_count/last_usage → Phase 2 selection。能记录“被引用”，不能证明“让任务变好”。

6.3 · XSkill

Experience Bank + Skill Library

同一视觉任务多次 rollout；visually grounded summary 与 cross-rollout critique 把局部 action guidance 和 task-level workflow 分成两条流。

multi-path rollouts → critique → Experience + Skill → visual adaptation → usage history
论文 / GitHub
6.4 · Trace2Skill

并行 patch → 层次化合并

success/error analyst 并行分析轨迹，产生 trajectory-local patches，再通过 merge tree 得到可迁移的 Skill directory，减少顺序编辑的依赖。

trajectory pool → parallel patches → hierarchical merge → portable SKILL.md
论文
6.5 · EvoSkills / CoEvoSkills

Generator–Verifier 共同演化

Generator 改 Skill，独立 Surrogate Verifier 产生逐项诊断；Oracle 只给隐藏结果，失败会促使 Verifier 加难后再迭代。

Skill version → verifier tests → diagnostics → revision → fresh oracle
论文 / GitHub
6.6 · MemSkill

Controller / Executor / Designer

Controller 选择 memory-operation skills，Executor 逐 span 构造 trace memory，Designer 从聚类后的 hard cases 修改 skill bank，并保留最佳 snapshot。

span → controller → executor → reward → hard-case buffer → designer
论文 / GitHub
6.7 · MemCon

学习何时 retrieve、re-retrieve 或 no-op

把 Memory 操作建模为 MDP/contextual bandit，按任务进度、是否 stuck、Memory 状态和历史结果在线选择操作与预算。

state(task + memory) → UCB action → backend → task reward → Q update
论文 / GitHub
6.8 · AFTER

跨任务、角色、模型的迁移

用 382 个 workplace tasks、六种角色和 22 类 Skill，分开测 local improvement、cross-task、cross-role 与 cross-model transfer。

versioned traces → refinement → transfer splits → specialization / generalization
论文 / 数据集
6.9 · ALMA

Meta Agent 搜索 Memory design

学习对象从一条 Memory 提升到可执行代码表达的 schema、更新和检索设计；每轮把 design、score、日志抽样放回 archive。

archive → reflect → implement → trial/debug → evaluate → archive
论文 / GitHub
6.10 · Causal Memory

把 decision → outcome 变成可检索关系

raw session log 经过 distill 形成 facts 和 causal edges，再与 BM25、semantic、entity、trace routes 汇合，回答“什么决定导致了什么结果”。

session → fact / causal edge → multi-route retrieval → lesson
固定仓库
6.10 · Omri / 基准

把结果、成本和持续评测放在同一条链

Omri 按 construction/retrieval/generation 计量 token、调用、延迟和能耗；MemoryAgentBench、Mem2ActBench、SkillsBench、ForgetEval 分别测读写、行动、Skill 与遗忘。

version → exposure/read/adopt → action/outcome → cost → next revision
Omri
反馈闭环的最小可追溯单位
讲解时抓住这一句

第六层的前沿不是“更多自动摘要”，而是把学习对象拆开：Experience、Skill、Verifier、Memory operation、迁移能力、Memory design 和成本账本，各自有不同的反馈输入和产物。

讲解收束 · 回到读者

读完六层，应该能回答五个问题

如果读者能沿着这五问走一遍，就已经理解了 Agent Memory 的真实架构，而不是只记住几个产品名。

01

输入是什么？

对话、工具、文档、代码，还是视觉/世界状态事件？它带了哪些项目和时间条件？

02

谁决定写入？

是 L1/Phase 1 抽取、Prompt 去重、Skill Review，还是 source-supported admission？

03

哪份状态是权威？

原始历史、current row、Markdown 正文、Skill version 和 FTS/vector/graph 投影是否分开？

04

怎样进入上下文？

直注、导航后读正文、Agent 工具检索，还是沿来源指针逐层下钻？

05

使用后变好了吗？

是 citation、真实采用、测试结果、跨任务迁移、Verifier 通过，还是只是被再次找到？

→

把答案交回六层

每个问题都能回到输入、形成、状态、管理、读取或反馈，而不是停留在抽象口号。

一句话带走：成熟的 Agent Memory 不是“存得更多”，而是让经历、状态、上下文和结果之间的关系可解释、可追溯、可继续演化。
