# 个人助手与长期对话：把“认识用户”变成可纠正的状态

个人助手中的 Memory 不只是把旧聊天塞回提示词。它处理的是跨会话仍有意义、又可能被用户纠正或撤回的信息：稳定偏好、明确约束、正在进行的事项、过往承诺，以及支撑这些结论的原始对话。这里的难点不是“是否能找回一句话”，而是让系统在合适的目的、时间和权限下使用仍然有效的信息。

## 这个场景保存什么

一条“用户喜欢素食”的记录，和一次“今天想吃素”的表述不是同一种对象。前者可能形成可编辑的偏好断言，后者首先是带时间和来源的事件。个人助手通常同时保留：

- 对话片段、工具结果和任务进度等情节证据；
- 明确说出或经多次互动支持的事实、偏好和约束；
- 本轮任务的工作上下文；
- 已使用过哪些记忆来生成建议或调用工具的关联记录。

把这些对象分层，是因为“当前画像”应能被修正，而原始证据不能在每次更新时被静默抹掉。MemMachine 的公开设计也把情节图、SQL profile 与工作记忆分开；Mem0 的固定版本则展示了从消息抽取事实、在带用户/代理/运行范围的过滤下写入和搜索的工程形状。[MemMachine](https://github.com/MemMachine/MemMachine) [Mem0](https://github.com/mem0ai/mem0)

## 场景组合：一次回答如何经过 write → manage → read → use

| 环节 | 个人助手里的组合 | 最突出的约束 |
|---|---|---|
| 写入 | 保存原话或工具事件，再抽取候选事实、偏好或待办 | 不能把一次试探、讽刺或模型猜测直接升格为身份事实 |
| 管理 | 合并重复证据、保留版本与冲突；处理纠正、撤回、过期和删除 | “新值已写入”不等于旧摘要、索引或计划已经失效 |
| 读取 | 先按用户、租户、目的、时间和可见性过滤，再做语义/关键词/实体检索 | 语义相关不等于该在本次回答中披露或使用 |
| 使用 | 将少量、当前有效的内容编译成回答或工具调用所需上下文 | 不能把完整私人档案交给模型，也不能让旧偏好悄悄驱动高影响行动 |
| 反馈 | 记录用户纠正、覆盖和行动结果，回流到状态与索引 | 纠正必须能追到已经派生的摘要、缓存和行动前提 |

可以把它想成一份会演化的个人档案：证据层回答“用户何时、怎样说过”，画像层回答“系统目前暂定什么”，而本轮上下文只携带完成此事所需的最小视图。后两层不应被误当作第一层的替代品。

```text
用户对话 / 工具结果
        │
        ├─ 原始情节与来源 ───────────────┐
        └─ 候选事实、偏好、约束 ──> 版本/冲突/同意管理
                                               │
当前请求 + 用户/目的/时间 ──> 范围过滤 ─> 检索与最小上下文编译
                                               │
                                         回答 / 工具行动
                                               │
                                  纠正、撤回、结果与依赖回写
```

## 常见的系统形状

| 形状 | 如何组合机制 | 能说明什么 | 主要边界 |
|---|---|---|---|
| 对话摘要 | 历史压缩为少量摘要，在下一轮直接注入 | 连续对话最直接 | 事实来源、冲突和过期通常不清楚 |
| 事实/偏好存储 | 从对话抽取离散断言，以过滤和检索供回答使用 | 便于更新、编辑与按范围读取 | 自动抽取会把推断和明示信息混在一起 |
| 情节 + 画像双层 | 原始事件保留，画像是可更新投影 | 同时支持追溯与当前个性化 | 需要处理投影滞后与删除传播 |
| 目的受限的上下文视图 | 检索后只向模型暴露获准字段 | 把隐私控制放到模型之前 | 需要把权限、目的和累计披露作为真正状态管理 |

近期工作把注意力从“记住更多”移向“纠正后能否改变行为”与“多轮回答会累积泄露什么”。[STALE](https://arxiv.org/abs/2605.06527) 的作者构造了 400 个冲突场景和 1,200 个查询；其最佳结果仍只有 55.2%，说明即使更新证据已经存在，代理仍可能按旧前提规划。这个结果只说明该协议中的失配，并不是所有个人助手的发生率。另一方面，[DP-MemView](https://arxiv.org/abs/2608.03130) 将重复的、受 Memory 条件影响的回答视为一个累计隐私问题，而不是一次脱敏就结束的问题。

## 工程实现中最容易被忽略的地方

表面相同的 `add`、`search` 和 `delete` 接口，背后可能是完全不同的系统。以 Mem0 的固定版本为例，写入路径会在范围过滤后检索既有候选、调用模型抽取事实、写向量记忆与 SQLite 历史，并尽力更新独立实体集合；不同后端是否支持关键词检索，会改变其混合搜索行为。这个代码事实不证明性能、隔离性或删除保证，却说明“同一个 SDK 接口”不能代表同一种能力。[v09 固定提交工程报告](../../../agent-memory-v09/bundle/projects/mem0ai-mem0.md)

个人助手还常需要一个行动前检查点：建议和工具参数应关联到所用画像版本；如果用户刚修正了地址、预算或授权，旧前提不能继续流入操作。这是个人化场景与普通长对话问答的分界：被检索到的记忆是否真的改变了后续行为，需要单独观察。

## 成熟度、失败与仍未解的问题

对话摘要、带用户范围的记忆 API、向量/关键词检索和可编辑 profile 已是常见工程形状。时间版本、纠正传播、目的限制读取和累计隐私控制则更不均匀：公开论文和项目分别展示了它们，但缺少在同一长期用户流、同一预算下的独立比较。

最常见的失败不是“完全遗忘”，而是错用：把一次性愿望当长期偏好；新旧事实并存时仍取旧值；语义相关的私人内容在不相关的场景出现；或删除后只从主表消失、却留在摘要、向量索引和缓存中。我们仍不知道自动画像相对只保留情节证据的长期净收益，也缺少把效用、纠正、越界披露、删除和真实工具行动放在同一协议里的独立证据。

相关机制可继续阅读：记忆对象与作用域、生命周期与遗忘、检索与上下文构造，以及安全与隐私专题；本页只解释它们在个人助手中如何相遇，而不把其中任何一种组合称为默认方案。
