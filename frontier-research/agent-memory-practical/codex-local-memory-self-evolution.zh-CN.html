OpenAI Codex · Local Memory

Codex 怎样从一次次对话里形成跨任务长期记忆

用户与 Codex 一问一答，期间产生消息、工具调用和执行结果。它们先维持当前任务，再被保存成历史记录；其中少量高价值经验会在之后经过两阶段提炼，进入一份可跨新任务读取的本地手册。

对话与工具轨迹→ 当前上下文→ Rollout 历史→ 长期提炼→ 管理与复用
从平时的一问一答开始 ↓

内容

一问一答与工具调用 当前 Thread 上下文 Thread 与 Rollout 历史 长期 Memory 何时开始 Phase 1 · 逐线程抽取 候选怎样管理 Phase 2 · 全局巩固 长期记忆怎样读取 引用与使用反馈 作用域与 Agent 边界 更新、忘记与清除 整体闭环

起点

平时使用 Codex，就是一问一答加上中间执行

长期 Memory 的输入并不是一个抽象的“rollout”。读者真正熟悉的起点，是用户消息、Codex 回复，以及完成任务过程中发生的工具调用和结果。

“修复刷新令牌撤销失效的问题。先复现，再修改，并确认并发刷新不会绕过撤销状态。”

输入

用户消息 + 已有 Thread 状态

本轮问题、约束、附件，以及同一 thread 前面已经发生的消息和工具结果。

处理

Agent 对话—执行循环

Codex 回复、选择工具、读取结果、调整判断，可能重复多次，直到任务结束或需要用户继续输入。

输出

新增事件 + 最终回复

本轮新增的 user/assistant message、tool call/result，以及呈现给用户的最终答复。

一次 turn 中真正发生的内容conversation + execution trace
user        修复 refresh token 撤销问题
assistant   我先定位认证链路并建立失败测试
tool_call  搜索 revoke / refresh token 的实现
tool_result 找到本地 revocation store
tool_call  运行认证测试
tool_result 并发刷新用例失败
tool_call  修改实现并再次运行测试
tool_result 新测试和相关回归通过
assistant   已修复；多实例必须使用共享撤销状态
输出去向：这些新增事件一方面进入当前 Thread，供下一轮继续；另一方面被追加进持久化历史，之后才可能成为长期 Memory 的输入。

第一层 · 当前任务

消息和工具结果先成为当前 Thread 的工作记忆

当用户继续追问“刚才那个测试为什么失败”时，Codex 不需要去长期 Memory 搜索。当前上下文已经保存了这轮对话和执行结果。

输入

当前 Thread 的可用历史

系统/开发者指令、本轮用户输入、前序消息、必要工具结果、项目环境，以及已注入的辅助内容。

处理

组装下一次模型上下文

Codex host 把当前仍需提供给模型的状态整理成下一次请求；模型据此继续当前任务。

输出

下一步回复或工具调用

例如解释刚才的测试失败、继续修改代码，或发起下一次工具调用。

例子：同一 Thread 的第二轮
新输入
user: 刚才为什么只有并发刷新测试失败？

当前上下文里已有
- 搜到的 revocation store 实现
- 第一次测试命令和失败输出
- Codex 对单实例/多实例差异的判断

输出
assistant: 单实例路径共享同一进程内状态；并发刷新经过不同实例，
           因而没有看到撤销记录。下一步应把撤销状态移到共享存储。
输出去向：新的回复和工具事件继续追加到同一 Thread。这里解决的是当前任务连续性，不会直接写入 MEMORY.md。

第二层 · 持久经历

Thread 结束以后，对话和执行过程仍保存为历史

Codex 内部把一条 thread 的持久化事件日志称为 rollout。这个词描述的是存储容器，不是另一种 Memory 内容。

输入

Thread 中持续产生的事件

每轮 user/assistant message、tool call/result，以及 cwd、branch、commit、时间和线程身份。

处理

按发生顺序持久化

Host 把事件追加到 rollout JSONL，并在 Thread DB 保存定位这条会话所需的索引和状态。

输出

Rollout 文件 + Thread 记录

前者是可回放的事件日志；后者让后台按 thread ID、来源、更新时间和路径找到它。

例子：这次认证修复在 Rollout 中大致怎样保存
{"type":"session_meta", "thread_id":"th-42", "cwd":"/repo/auth-service"}
{"type":"turn_context", "git_branch":"fix/token-revoke", "git_sha":"8c4a1d9"}
{"type":"message", "role":"user", "text":"修复 refresh token 撤销问题"}
{"type":"message", "role":"assistant", "text":"我先建立失败测试"}
{"type":"tool_call", "name":"exec", "args":"pytest tests/test_refresh.py"}
{"type":"tool_result", "call_id":"call-17", "text":"1 failed, 8 passed"}
{"type":"tool_call", "name":"apply_patch", "args":"..."}
{"type":"tool_result", "call_id":"call-18", "text":"patch applied"}
{"type":"message", "role":"assistant", "text":"修复并验证完成"}

字段和值为说明性示例；关键是看清它保存的是事件序列，不是一篇已经整理好的记忆文章。

输出去向：恢复旧 Thread 时，它用于重建历史；生成长期 Memory 时，后台先从 Thread DB 选中这条记录，再打开对应 rollout。整份 JSONL 不会原样交给 Phase 1。

第三层 · 长期 Memory 形成入口

历史任务不会在结束一刻立刻变成长期记忆

旧 thread 先成为持久历史；当之后有一个合格的根 Agent turn 启动时，它只负责唤醒后台流水线，真正被处理的来源仍是之前已经空闲的 thread。

本页描述的是 Local Memory 功能启用后的路径。固定版本中 MemoryTool 虽标为 Stable，但默认关闭；只有相应生成与读取开关生效，后台提炼和新 thread 注入才会发生。
输入

启动信号 + Thread 候选表

一个新的根 Agent turn 唤醒后台；Thread DB 提供历史 chat 的 ID、来源、更新时间、归档状态、memory mode 和 rollout 路径。

处理

Eligibility 筛选与认领

检查功能开关、额度、chat 来源、年龄、空闲时间、是否当前线程、是否归档，以及 source watermark 是否已经处理。

输出

待执行的 Phase 1 Jobs

本次最多认领两个历史 thread，为每个 thread 建立或更新 job、ownership token 和 lease；也可能一个都不选。

10 天默认只扫描近期更新的 rollout
6 小时默认空闲门槛
2 个每次 startup 最多认领的 rollout
25%默认剩余额度保护阈值
例子：四条历史 Thread，哪条会进入本轮 Phase 1
th-42  auth fix          8 小时前更新   enabled   根线程  → 认领
th-43  ongoing refactor  20 分钟前更新  enabled   根线程  → 跳过：仍活跃
th-44  quick question     2 天前更新     disabled  根线程  → 跳过：不允许生成
th-45  subagent trace     1 天前更新     enabled   子线程  → 跳过：非根 Agent

本轮输出：
job { kind: "phase1", thread_id: "th-42", status: "running",
      ownership_token: "owner-a7", lease_expires_at: "..." }
输出去向：被认领的 thread ID、rollout 路径和 job ownership 交给 Phase 1 Worker；刚刚唤醒后台的新 turn 本身不是这次抽取的内容。

长期 Memory · 单任务提炼

Phase 1 从一条历史 Thread 中提炼单任务经验

它先从 rollout 日志恢复这次任务的消息和执行轨迹，再过滤、脱敏和截断，最后回答三个问题：任务发生了什么、结果怎样、其中什么值得未来复用。

输入

一条被认领的历史 Thread

thread ID、rollout 文件、cwd/branch/commit、source watermark，以及本次抽取模型和上下文预算。

处理

过滤后进行一次 LLM 抽取

保留 user/assistant message、tool call/result 和主线程中的 Agent 通信；排除控制记录、developer、完整 AGENTS/Skill 注入，脱敏并按预算截断。

输出

三个单任务派生字段

rollout_summary、rollout_slug、raw_memory，随后写入 stage1_outputs。

例子：认证修复 Thread 进入 Phase 1 前后
送给抽取模型的主要输入
────────────────────
scope: cwd=/repo/auth-service, branch=fix/token-revoke, sha=8c4a1d9

[user] 修复 refresh token 撤销失效；先复现并覆盖并发刷新。
[assistant] 我先定位认证链路并建立失败测试。
[tool] pytest tests/test_refresh.py → 1 failed, 8 passed
[assistant] 单实例内存撤销表无法覆盖跨实例并发刷新。
[tool] apply_patch → patch applied
[tool] pytest tests/test_refresh.py tests/test_auth.py → 19 passed
[assistant] 修复完成；撤销状态已移到共享 store。

Phase 1 输出
──────────────
{
  "rollout_slug": "auth-token-revocation-shared-store",
  "rollout_summary": "在 auth-service 中复现并修复 refresh token
    跨实例撤销失效；新增并发刷新测试，19 项认证测试通过。",
  "raw_memory": "项目：/repo/auth-service。Refresh token 撤销必须使用
    多实例共享 store；进程内 Map 只适合单实例测试。修改前先运行
    tests/test_refresh.py 复现，修改后同时运行 refresh 与 auth 回归。
    来源：thread th-42，branch fix/token-revoke，commit 8c4a1d9。"
}

示例内容用于展示字段语义，不是仓库内置模板。三个字段的结构固定，具体文字由抽取模型生成。

名字里的 raw_memory 并不是原始对话。它已经是模型派生文本；真正的原始证据仍是 rollout JSONL。理解这一区别，才能在出错时回到来源，而不是把派生摘要当成原话。
被认领不等于一定“记住”。Phase 1 的形成规则允许不产出有价值内容：一次性的修补、没有稳定结论的探索或不值得未来复用的任务，可以不进入后续长期手册。
输出去向：这三个字段还不是最终长期 Memory。它们作为一条 Stage 1 候选进入 memories_1.sqlite，等待后续选择与跨任务巩固。

长期 Memory · 候选管理

Phase 1 的输出先成为候选，不会立刻进入长期手册

Codex 把“原始历史”“单任务候选”“后台任务状态”和“最终可读知识”拆开管理。这样既能重试和增量处理，也不会把一次模型抽取直接当成全局真相。

输入

Phase 1 结果 + 来源状态

三个派生字段、thread ID、rollout path、source updated_at/watermark、cwd/branch 等元数据，以及当前 job ownership。

处理

Upsert 候选并完成 Job

把单任务结果写入 stage1_outputs，记录它对应的来源版本；更新 Phase 1 job 的成功状态、retry 和错误信息。

输出

可选择的 Stage 1 Row

它拥有内容、来源、生成时间、usage_count、last_usage 和 selected_for_phase2 等管理字段。

例子：th-42 写入候选库后的记录
stage1_outputs
{
  thread_id: "th-42",
  source_updated_at: "2026-08-23T08:10:00Z",
  rollout_slug: "auth-token-revocation-shared-store",
  rollout_summary: "在 auth-service 中复现并修复跨实例撤销失效...",
  raw_memory: "Refresh token 撤销必须使用多实例共享 store...",
  generated_at: "2026-08-23T14:20:00Z",
  usage_count: 0,
  last_usage: null,
  selected_for_phase2: false
}

jobs
{ kind: "phase1", thread_id: "th-42", status: "succeeded",
  input_watermark: "2026-08-23T08:10:00Z", retry_count: 0 }
Watermark

判断来源有没有变化

同一 thread 后来继续发生新 turn 时，新的 source watermark 会使它重新具备抽取资格。

Usage fields

判断候选以后是否常用

初始 usage 为零；未来回答真正引用它后，计数和最近使用时间才会改变。

输出去向：Phase 2 不扫描所有 rollout；它从这些 Stage 1 rows 中按使用与新近性选候选。原始 rollout 仍留在原处，作为可回溯证据。

长期 Memory · 跨任务巩固

Phase 2 把多条单任务候选整理成一份全局手册

它不是简单拼接摘要，而是从候选池选一批仍值得保留的经历，比较新旧差异，再让一个受限内部 Agent 对长期工件做去重、合并、修正和压缩。

输入

候选池 + 旧 Memory 工作区

最多 256 条 Stage 1 rows、已有 MEMORY.md/memory_summary.md/skills、用户 ad-hoc notes，以及上次成功 Git baseline。

处理

选择、物化、对比、巩固

先按 usage 与新近性选择；再写 raw/rollout summaries、生成相对旧基线的 diff；最后由受限 Agent 去重、合并、修正和压缩。

输出

长期文件 + 提交状态

更新短索引、长期手册、任务摘要和可选 skills；验证后重置 Git baseline，并原子更新 Phase 2 job watermark 与 selected flags。

例子：两个单任务候选怎样改变长期手册
Phase 2 输入
─────────────
旧 MEMORY.md：
  ## /repo/auth-service
  - Token 撤销使用本地 Map。

候选 th-42：
  - 跨实例并发刷新证明本地 Map 不可靠；应使用共享 store。
  - refresh + auth 共 19 项测试通过。

候选 th-51：
  - 认证改动后应运行 tests/test_refresh.py 和 tests/test_auth.py。

用户 note：
  - “忘记本地 Map 是可接受生产方案；它只允许用于单实例测试。”

Phase 2 输出
─────────────
MEMORY.md：
  ## /repo/auth-service
  ### Token revocation
  - 生产与多实例环境必须使用共享 revocation store。
  - 进程内 Map 仅适用于单实例测试。
  - 修改撤销逻辑后运行：
    `pytest tests/test_refresh.py tests/test_auth.py`
  - 证据：th-42、th-51。

memory_summary.md：

示例展示数据流：旧结论被修正，两条经历被合并，短索引只保留导航。具体文件措辞由 Consolidation Agent 生成。

Phase 2 最终管理的文件reader-facing memory workspace
~/.codex/memories/

├── MEMORY.md                # 跨任务长期手册
├── raw_memories.md          # 本轮选中 Stage 1 派生内容的物化输入
├── rollout_summaries/       # 每条选中经历的摘要和 rollout 指针
├── skills/                  # 适合独立复用的流程工件
└── extensions/ad_hoc/       # 用户 remember/update/forget notes
没有

网络和外部服务

内部 Agent 在受控环境中不能访问网络，也没有 MCP、Apps 或 Plugins。

没有

递归 Memory 与协作

它自身是 ephemeral，不读取当前 Memory，也不能再调用 Subagent，避免形成递归巩固。

只有

Memory root 写权限

cwd 被限制到本地 Memory 工作区；ownership 丢失后不能把结果提交成新基线。

操作可靠性较强

lease、heartbeat、watermark、sandbox、symlink 拒绝和 Git baseline 都由确定性代码执行。

语义可靠性仍生成式

合并什么、怎样处理冲突、何时删除旧结论仍由模型判断；最终检查不会验证每句话是否仍有当前证据。

输出去向：memory_summary.md 会在未来新 Thread 中作为入口注入；其余文件留在本地 Memory root，等待 Agent 按需搜索和读取。

长期 Memory · 重新读取

全新的 Thread 不继承全部旧对话，只获得长期记忆入口

Codex 不会把所有 rollout 和整本手册塞进新上下文。它先注入一份短索引，当前 Agent 再按项目和问题逐层搜索长期手册、任务摘要和原始证据。

输入

新任务 + 常驻短索引

当前 user message、cwd/项目状态，以及最多 2500 tokens 的 memory_summary.md；整本 MEMORY 和旧 rollout 不会自动注入。

处理

Agent 主动逐层读取

先根据短索引判断是否相关，再用关键词搜索 MEMORY.md；需要精确步骤或证据时继续打开 skill、rollout summary 或原始 rollout。

输出

Memory 上下文 + Citation

读取到的相关文件片段进入当前推理；最终回答附带实际文件行和 rollout IDs，供系统解析使用反馈。

例子：新 Thread 怎样找回认证经验
新输入
──────
cwd: /repo/auth-service
user: 按我们之前验证过的方式修改 refresh token 撤销逻辑。

已经注入的 memory_summary.md
────────────────────────────
- auth-service：Token 撤销、共享 store 与认证回归流程，见 MEMORY.md。

Agent 读取过程
──────────────
1. search("auth-service token revocation shared store")
2. 命中 MEMORY.md 中 Token revocation 段落
3. read(MEMORY.md, 对应行范围)
4. 若需确认旧测试证据，再读：
   rollout_summaries/auth-token-revocation-shared-store.md

读取得到
────────
- 生产/多实例使用共享 revocation store
- 本地 Map 仅限单实例测试
- 回归命令：pytest tests/test_refresh.py tests/test_auth.py
- 来源 thread：th-42、th-51

输出
────
assistant: 我会沿用共享 revocation store，并先运行 refresh 失败用例；
           修改后执行 refresh 与 auth 两组回归。
citation data: MEMORY.md 对应行；rollout_ids=["th-42","th-51"]
list查看 Memory 根下允许访问的文本工件。
read按路径和行范围读取需要的具体内容。
search用关键词在文件中定位任务族、错误文本和项目经验。
add_ad_hoc_note记录用户明确提出的 remember、update 或 forget 请求。
检索是否成功，很依赖 Phase 2 怎样命名标题和保留关键词。若巩固 Agent 把用户原词改写成过度抽象的概念，即使事实仍在文件里，substring search 也可能找不到。
Dedicated Memory tools 不是唯一读取路径。工具关闭时，主 Agent 仍可以按照只读指令，用普通文件搜索打开 Memory root；无论哪条路径，都不能越过路径、隐藏文件和 symlink 边界。
输出去向：相关 Memory 片段只进入当前 Thread 的本轮上下文；citation 中的 rollout IDs 会进入下一步 usage 反馈，不会把当前回答自动写回长期手册。

长期 Memory · 使用管理

Citation 不只是展示，它会改变以后保留什么

Codex 已经有一条很轻量的反馈环：某条历史经验被新任务真正引用后，对应候选会得到使用信号。

输入

最终回答中的 Citation Data

实际读取的 Memory 文件行，以及这段内容指向的 rollout/thread IDs。

处理

解析并回查 Stage 1 Rows

把可见回答与引用数据分开，验证 ID，再对被引用的候选增加 usage 并刷新 last_usage。

输出

新的候选使用状态

更新后的 usage_count/last_usage 会参与后续 Phase 2 排序，使被引用候选更可能继续保留。

例子：th-42 被新任务引用以后
输入 citation data
{ files: [{ path: "MEMORY.md", lines: "18-27" }],
  rollout_ids: ["th-42", "th-51"] }

更新前
th-42  usage_count=0  last_usage=null
th-51  usage_count=2  last_usage=2026-08-20

更新后
th-42  usage_count=1  last_usage=2026-08-25
th-51  usage_count=3  last_usage=2026-08-25

以后 Phase 2 排序时：
usage_count DESC → last_usage/source recency DESC → source recency DESC

已经闭合的部分

  • 引用能够回到 rollout 候选；
  • 使用次数和最近使用时间被持久化；
  • 这些字段真实参与下一轮 selection；
  • 整个环路可观察、可解释。

仍然缺少的部分

  • 没有记录“被展示但未采用”的曝光；
  • 没有把引用归因到最终任务质量；
  • 遗漏 citation 就没有使用信号；
  • 常被找到的内容可能进一步获得曝光优势。
这不是 learned retriever，也不能证明“被引用的 Memory 让任务变好”。它只实现了 citation-driven retention：使用过的内容更容易继续进入巩固。
输出去向：usage 更新回到候选库，而不是直接改写 MEMORY.md。下一次 Phase 2 才会根据新的候选排序重新生成文件。

长期 Memory · 作用域管理

一个全局物理库，主要靠文档组织做项目路由

不同项目没有独立 Memory 根。cwd、branch、commit 和文档中的 task groups 负责表达逻辑作用域，最终仍由主 Agent 判断当前该读哪一块。

输入

当前项目条件 + 全局 Memory

新 thread 的 cwd/branch/commit 和任务文本，以及同一个 CODEX_HOME 下的全局 summary 与长期手册。

处理

按文档标签做逻辑路由

Agent 根据 summary 中的项目/任务族标题选择读取区域；文件系统没有按当前 cwd 强制隔离出独立 Memory root。

输出

被选中的项目片段

理想情况下只读取当前项目相关内容；若文档丢失 scope 条件，其他项目或旧 worktree 经验也可能被误用。

例子：同一全局手册里有两个项目
当前输入
cwd=/repo/auth-service
branch=fix/token-revoke
user=修改 refresh token 撤销流程

全局 memory_summary.md
- /repo/auth-service：Token 撤销与认证回归
- /repo/billing-service：退款幂等键与账务回滚

处理
→ 当前 cwd 与任务命中 auth-service
→ 只读取 MEMORY.md 的 Token revocation 段

输出
→ 共享 revocation store + refresh/auth 回归流程
→ 不应读取 billing-service 的退款流程
Subagent

非根 Agent 不会独立触发 Memory Writer；但它回传到主 rollout 的 inter-agent communication 可能随主任务被记住。

Guardian

复核 session 明确关闭 Memory 使用和专用工具，使审批判断不直接受个人历史经验影响。

这套 scope 更接近“全局操作手册中的项目章节”，不是数据库层面的 tenant/project 隔离。若巩固时丢掉 branch 或 commit 条件，旧分支经验可能被另一个 worktree 误用。
输出去向：作用域判断只影响当前 Agent 读取哪些内容，不会移动或复制 Memory 文件。所有项目仍共享同一个本地 Memory root。

长期 Memory · 更新与清除

关闭、忘记和 Reset 是三件不同的事

Codex 的更新与删除不是稳定 entry ID 上的同步 CRUD，而是通过资格控制、追加说明和全局重写来完成。

输入

用户或产品控制动作

对某条 chat 设置是否贡献 Memory；明确提出 remember/update/forget；或者请求 full reset。

处理

走三条不同路径

Chat mode 更新 Thread 资格；显式语义更新追加 ad-hoc note；reset 先清 Memory DB，再清本地生成文件。

输出

资格、Note 或清空状态

它们分别影响未来抽取、下一次 Phase 2 的输入，或当前生成式 Memory；没有一个等于删除原始 rollout。

例子：三个看似都叫“不要记”的动作，输出完全不同
A. 当前 Chat 不贡献未来 Memory
输入：set thread th-42 memory_mode=disabled
输出：th-42 以后不再成为新的 Phase 1 输入
不影响：已经写入 MEMORY.md 的 Token revocation 段

B. 忘记一个已经形成的结论
输入：user 明确说“忘记本地 Map 可用于生产；它只允许单实例测试”
输出：extensions/ad_hoc/notes/2026-08-25-....md
      内容记录这条 forget/update 请求
下一步：Phase 2 读取 note + 旧 MEMORY.md，由模型改写手册和短索引

C. Full reset
输入：reset local memories
输出：清空 memories_1.sqlite 中的 Stage 1 rows/jobs，随后清 Memory 文件
仍保留：原始 thread/rollout 与它们的 memory_mode
结果：仍在资格窗口内的旧 thread，之后可能再次被 Phase 1 抽取

所以 Thread disable、语义 forget 和 full reset 的输入、输出、影响范围都不同。

Reset 的数据库删除和文件清理也不是跨介质原子事务。如果第二步失败，可能出现候选已经清空而旧文件仍在的中间状态。
输出去向：ad-hoc note 会成为下一轮 Phase 2 的强制输入；thread mode 只回到 eligibility；reset 只清当前生成状态。这里尚没有带稳定 entry ID 的同步删除结果。

整体总结

Codex 怎样形成一条本地经验演化闭环

它不是“把聊天存进向量库”，而是把历史任务转换成一份由后台 Agent 维护、由新任务按需阅读的个人工作手册。

对话与执行

用户消息、Codex 回复、工具调用和结果首先服务于当前 turn。

当前任务连续

多个 turn 组成 thread；前序消息和工具结果继续支持后续一问一答。

历史持久化

Thread 的事件过程保存为 rollout，并带有 cwd、branch、commit 等条件。

进入长期形成

历史 thread 满足年龄、空闲和 Memory mode 条件，等待后续 root turn 唤醒。

逐线程抽取

Phase 1 过滤与脱敏后，生成任务摘要和派生经验。

全局巩固

Phase 2 选择候选，用受限 Agent 更新手册、索引与技能。

渐进读取

新线程先见 2500-token 短摘要，再词法搜索和打开证据。

使用反馈

Citation 回写 usage，影响候选是否继续进入未来巩固。

这套系统当前做到哪里

已经较完整的工程主干

  • 线程筛选、watermark、lease、retry 与后台 job；
  • 两阶段形成与增量文件巩固；
  • 受限写入、只读访问和路径安全；
  • 短摘要、词法搜索、渐进披露和行级 citation；
  • citation 驱动的使用保留反馈。

仍然没有闭合的语义问题

  • 生成内容的事实正确性、冲突与时间更新；
  • 项目/worktree 的硬作用域；
  • 逐项 inspect/update/delete 与可验证派生删除；
  • DB selection 与文件读取的一致快照；
  • 使用反馈到最终任务质量的可靠归因。

怎样判断一次 Memory 更新真正进入了后续任务

01
确认来源被认领

检查目标 thread 是否满足 eligibility，以及 Stage 1 job 是否处理到正确 source watermark。

02
确认候选与手册发生变化

区分 memories DB 中的 Stage 1 输出、rollout summary、MEMORY.md 和短索引分别更新到哪里。

03
确认新线程真的获得索引

功能开关和 use_memories 必须生效，短摘要才会作为上下文进入新线程。

04
确认 Agent 实际读取

查看 search/read 路径与最终 citation，不能把“内容存在”当成“内容被使用”。

05
最后才讨论任务效果

Usage 只证明引用发生；任务是否更快、更正确或更少返工，是另一层尚未由当前闭环自动回答的问题。

Codex 先用对话上下文维持当前任务，用 rollout 保存原始经历，再从其中提炼和管理跨任务长期记忆。新的 thread 不继承全部旧对话，而是先获得短索引，需要时再逐层回到长期手册、任务摘要和原始证据。

本页解释固定版本中可见的本地 CLI/App/IDE host 机制，不包含模型权重、隐藏云端调度、真实用户 Memory 内容，也不把代码路径存在表述为实际任务收益。
