# 多 Agent 共享 Memory：共享内容之前，先共享边界

多 Agent 系统的难题不是让更多代理看见同一个向量库，而是让每个记忆对象在多个主体、多个副本和不断变化的权限下，仍可说明“谁写的、谁能读、哪个版本有效、撤回后修到哪里”。共享 Memory 因此同时是状态管理、权限治理和互操作问题。

## 这个场景保存什么

除了普通的事实、事件和技能，多 Agent 场景还保存共享关系本身：主体和租户、资源范围、读写授权、来源链、版本与父版本、冲突状态、复制位置，以及已被哪些计划或技能使用。个人私有片段、团队共享决定和可迁移技能不应因为都能被检索就被压入一种“公共 Memory”。

| 层 | 典型对象 | 在链路中的职责 | 关键问题 |
|---|---|---|---|
| 私有层 | 单个代理的会话、草稿、局部观察 | 限制可见范围，保留工作上下文 | 何时可提升为共享内容？ |
| 共享状态层 | 经确认的事实、决定、任务事件 | 支持协作检索与一致行动 | 并发修改、冲突、陈旧副本如何处理？ |
| 共享技能层 | 可复用程序、策略或工具经验 | 让经验跨代理迁移 | 不可信轨迹何时能获得行动权？ |
| 治理与便携层 | 主体、权限、来源、版本、删除/撤回状态 | 约束读写、同步和导入导出 | 接口兼容是否真的保留语义？ |

## 场景组合：共享系统的 write → manage → read → use

```text
各 Agent 的观察 / 工具结果 / 任务产物
                 │
     主体、范围、来源、写入权检查
                 │
       私有记录 ──> 共享候选 ──> 权威事件/版本日志
                                           │
                         派生索引、摘要、复制副本、可共享技能
                                           │
请求 Agent + 当前目的 + 权限版本 ──> 过滤 / 冲突解析 / 检索
                                           │
                              上下文与行动前授权 ──> 工具或协作行动
                                           │
                           结果、撤权、冲突和删除修复回写
```

这个结构中的“权威事件/版本日志”与“派生索引”必须分开：索引可以重建，权限和来源不能靠相似度猜测。读操作也不只是查询条件；它要使用请求主体、代理身份、目的和当时的权限版本来决定候选集合，随后才谈排序和上下文长度。

## 主要方案形状

| 形状 | 如何组合机制 | 已展示的价值 | 尚未解决的部分 |
|---|---|---|---|
| 共享对话池 | 过滤、存储、检索与中介器围绕一个共享池协调 | 让不同代理从交互历史中取回协作线索 | 共享本身不定义权限、冲突或删除语义 |
| 私有/共享分层 | 片段在私有与共享层间移动，并携带来源和读写策略 | 适合表示“谁可见、何时可写” | 动态撤权、跨副本修复仍需完整链路 |
| 事件日志 + 可重建投影 | 把共享状态写成带版本的事件，索引和摘要为投影 | 有利于追溯、合并和恢复 | 需要明确并发模型和权威归属 |
| 可移植记录/协议 | 用 schema、适配器或传输层交换 Memory 对象 | 改善导入导出与跨工具连接 | transport、record、检索和生命周期不是同一层的标准 |

[INMS](https://arxiv.org/abs/2404.09982) 描述了由过滤、存储、检索和从交互历史改进的检索中介器组成的共享对话池；[Collaborative Memory](https://arxiv.org/abs/2505.18279) 则显式区分私有与选择性共享片段，并把来源、随时间变化的读写策略放在共享边界上。二者说明共享需要的不仅是存储，但都不能单独证明组织级一致性、隔离或删除已经闭环。

工程层的项目也在探索不同切面：有的以服务/API 管理 scope，有的以本地人类可读文件承载记忆，有的试图定义可交换记录。它们的接口动词可能相似，但 `remember`、`delete`、`share` 在冲突处理、派生索引、备份和授权检查上的语义未统一。MCP 可以提供连接方式，却不自动定义 Memory 的记录模型、检索语义或撤回传播。

## 约束为何在这个场景最突出

共享会放大普通单代理问题。一次错误写入可能被多个代理检索；一次撤权可能要修复索引、摘要、缓存、已分发的技能和正在执行的计划；一次离线修改回流时可能覆盖别人的新状态。尤其是共享技能：它不是“多了一条文本”，而是可能在之后影响工具调用的长期资产。

因此需要将四个阶段分别看待：内容被写入、内容被提升为共享、内容被分发到副本、内容获得行动影响力。把它们合成一个信任分数会掩盖错误发生的位置。近期关于共享记忆与多主体权限的研究把范围、主体与权限视作显式状态；但在当前公共材料里，跨实现的动态权限、冲突、撤回、删除修复和行动后果仍缺少固定协议下的独立比较。

## 工程现实与近期信号

近期变化主要是更多项目将 Memory 暴露为 MCP/HTTP/文件接口，并尝试把来源、scope、版本或 schema 放到记录中。它们是值得跟踪的互操作信号，但不意味着已经出现通用的组织级契约：当前证据中缺少两个独立组织固定到同一规范版本的完整互通报告，也缺少双方导入导出后对字段与生命周期不变量的 round-trip 证据。

对读者而言，这意味着“共享”不能被当作单一能力标签。较成熟的是基本的范围过滤、服务接口和事件式记录；证据较薄弱的是多副本合并、动态撤权、派生物删除、跨实现可携带性以及共享技能的抗投毒闭环。仍未解决的问题不是“还有没有新的协议名称”，而是这些语义能否在真实并发、断网、权限变化和行动影响下被一致执行。

相关机制可继续阅读：记忆对象与作用域、生命周期、安全治理、经验/技能，以及互操作和工程集成专题。本页没有把任何共享拓扑或协议标为推荐路线。
