# 评测与 Benchmark：Memory 的好坏必须落在一次完整行动上

Memory 的评测看似是在问“能否找到旧信息”，实际上是在问一条链路能否可靠地把过去带到现在：系统写入了什么、管理阶段是否保留了可用证据、读取时是否找对并组织好、行动时是否因此做对且没有越权。只测最后的问答分数，会把写入漏失、陈旧状态、检索偶然命中和不安全行动混成一个数字。

本篇把评测看作贯穿 `write → manage → read → act` 的观察框架，而不是给不同项目排总榜。结论以 2026-08-10 前已核验的材料为限。

## 一条记忆为何会被“测错”

设想一个 Coding Agent 昨天已读到“部署脚本必须使用新凭据”，今天它修改脚本。若它失败，原因可能是：事件没有写入；摘要合并时漏了条件；搜索只取到旧版本；上下文被工具输出挤掉；或模型虽然看到新事实却仍调用了旧命令。一个单一 QA 分数不能区分这些原因。

```text
事件/对话/工具结果
       │ write: capture、来源与作用域
       ▼
原始记录 ── manage: 提炼、版本、遗忘、重建 ──► 派生记忆/索引
       │                                             │
       └───── 可回查证据 ◄── read: 召回、排序、编译 ┘
                                                     ▼
                                      回答 / 工具调用 / 环境状态改变
                                                     │
                                        act: 结果、伤害、成本与轨迹
```

这张链路也解释了为什么“检索指标高”不是终点：它可以在不该读取的租户数据上取得高分；“回答正确”也未必代表系统会把正确知识转换为正确行动。

## 评测家族各在看什么

| 评测家族 | 主要观察点 | 能揭示 | 容易遗漏 | 成熟度与证据边界 |
|---|---|---|---|---|
| 长期对话 / QA | 跨会话事实、时间与偏好回忆 | read 的召回和回答质量 | 写入遗漏、工具行动、权限 | 最常见；协议、模型和预算差异很大 |
| 检索与上下文消融 | raw、摘要、索引、候选深度、token 预算 | manager/reader 的因果贡献 | 真实开放环境的副作用 | 方法较清楚，但尚无统一成本账本 |
| 经验 / Agent 任务 | 过去轨迹能否改善新任务 | 记忆到行动的迁移 | 不安全或错误泛化 | 正在增长，验证器与环境差异显著 |
| 环境 / 世界状态 | 状态更新、过时事实、多步工具行为 | temporal 管理和 action grounding | 私密性、长周期维护 | 较早期，通常只覆盖特定环境 |
| 安全生命周期 | 写入投毒、读出诱导、执行及删除 | 安全控制是否贯穿生命周期 | 通用效用与真实组织风险 | 近一年快速出现，指标不可互换 |
| 工程 harness | 后端插件、备份恢复、生命周期隔离 | 实验是否可复现、后端是否可插拔 | 不能单独证明算法更好 | 早期但很重要；harness 不是分数权威 |

`LongMemEval` 的 500 个长期交互问题把 indexing、retrieval、reading 分开呈现；`LongMemEval-V2` 把范围扩展到网页 Agent 的经验任务。它们适合定位长时程读出问题，但不应被解读为所有类型 Memory 的总排名。[LongMemEval](https://arxiv.org/abs/2410.10813) [LongMemEval-V2](https://arxiv.org/abs/2605.12493)

近期的 `OmniMemEval` 提供 user-memory 与 agent-memory 两条轨道，并把插件生命周期、清理与备份恢复放进 harness；它证明“可替换后端的实验底座”正在出现，不证明某个插件在所有基准上更强。[OmniMemEval](https://github.com/MemTensor/OmniMemEval)

## 同一份记忆，需要分段观察

| 阶段 | 核心问题 | 可观察量 | 典型反证 |
|---|---|---|---|
| 写入 | 该捕获的事件是否真正进入带来源的记录？ | capture recall、重复率、来源/主体/时间完整性、写入延迟 | hook fail-open 时，宿主继续运行而 capture 缺失 |
| 管理 | 摘要、合并、遗忘与版本是否损失关键条件？ | source-span coverage、冲突/陈旧处理、重建率、派生物滞后 | 短摘要提高覆盖率/Token，却漏掉查询关键细节 |
| 读取 | 正确证据能否在正确作用域、时间和预算内被拿到？ | oracle/evidence recall、nDCG、授权拒绝率、candidate depth、compiled tokens | 改变 retriever 或候选深度可改变结论 |
| 行动 | Agent 是否正确、可追溯且安全地使用证据？ | task/action success、工具参数正确性、abstention、错误副作用 | QA 正确不等于真实工具调用正确；“已更新”不等于行为不陈旧 |
| 运维 | 结果能否复现，代价是否可解释？ | p50/p95 write/read/compile、LLM 调用、存储、重建、失败恢复 | 只公布 tokens saved 或单次平均延迟 |

这里的“oracle/evidence recall”指被测任务所需的原始证据是否被找到；它与模型答案正确率不同。二者的差距往往正是 context compiler、模型推理或工具使用的误差。

## 比较必须先固定协议

目前最明确的反证来自对 LightMem 的独立复现：在固定构造出的记忆库上，替换 retriever 即可显著影响答案；在匹配的 retrieval depth 下，raw-turn Naive RAG 通常更强，而构造记忆在紧答案 token 预算时才显示优势。这并不是“摘要无用”，而是说明结论依赖 retriever、候选量、编译预算和读者模型，不能把作者论文的数字抽离协议后做总榜。[Reproducing LightMem](https://arxiv.org/abs/2607.29104)

因此，两份系统实验即使都叫“准确率”，也只有同时固定或完整报告下列变量时才可直接比较：数据集及版本、记忆访问权限、模型和提示、原始/派生存储、retriever、`candidate_k`、reranker 深度、编译后的 memory token、回答与工具输出预算、裁判、随机种子以及运行环境。静态 QA、网页 Agent、具身环境和安全攻击的分数不应被拼成排行榜。

## 安全指标尤其不可跨协议拼榜

`MemSecBench` 将攻击链明确为 Write–Execute–Forget，并在 310 个案例、48 个上下文和 24 个配置中考察持久 Memory 的安全性；这类 benchmark 的贡献是把安全放回生命周期。[MemSecBench](https://arxiv.org/abs/2607.27080)

但例如 AgentPoison 的攻击成功率、Sleeper 的“成功取回条件下”恶意动作比例、PoisonedEvolution 的技能演化成功率，分母与被测阶段不同：前者可能涉及投毒触发，后者可能只度量持久工件被修改。它们不能互相替代，更不能和普通 QA 成绩合并。[AgentPoison](https://arxiv.org/abs/2407.12784)

## 当前状态、近期变化与未解问题

当前主流仍是长期 QA/检索型评测；近 12 个月的变化是把经验任务、后端生命周期、环境状态与安全链路纳入评测表面，近 90 天的弱信号是安全 benchmark 与跨插件 harness 同时加速。它们尚未形成共同的跨后端成本—质量—安全协议。

相对稳固的共识是：评测需要报告访问路径和预算，且原始证据的保留/回查能力不应被流畅摘要掩盖。证据较弱的部分是“哪一种 memory operator 普遍更优”；现有结果多依赖作者环境，独立的同任务、同模型、同预算、同后端复现仍少。

最重要的开放问题不是再增加一个总分，而是建立能同时覆盖 source coverage、时间/冲突正确性、授权拒绝、行动结果、延迟、存储和修复成本的可复现实验账本。没有它，就无法可靠判断一个复杂生命周期系统相对 scoped raw retrieval 的净收益，也无法知道提升是来自记忆机制还是来自更宽的检索、更多 token 或不同的模型。

## 证据与阅读边界

- LongMemEval / LongMemEval-V2：长期交互与网页 Agent 经验任务，[论文](https://arxiv.org/abs/2410.10813) 与 [V2 论文](https://arxiv.org/abs/2605.12493)。
- OmniMemEval：插件化评测框架，[仓库](https://github.com/MemTensor/OmniMemEval)。
- LightMem 独立复现：检索器和 token 预算混杂因素，[论文](https://arxiv.org/abs/2607.29104)。
- MemSecBench：Write–Execute–Forget 安全生命周期，[论文](https://arxiv.org/abs/2607.27080)。

这些来源支撑本文的协议与边界判断；它们并不构成某种 Memory 系统的统一排名或部署建议。
