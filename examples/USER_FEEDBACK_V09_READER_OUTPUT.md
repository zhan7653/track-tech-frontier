# 用户反馈与已确认输出契约：v09 的研究材料尚未转化为真正面向读者的成品

**确认日期：** 2026-08-12

**适用对象：** `Agent Memory frontier research v09` 及 `track-tech-frontier` 后续输出设计

**性质：** 新增反馈及后续 Grill 确认的 v10 输出契约；不覆盖此前关于输入广度与研究综合的反馈

## 一、核心结论

v09 已经积累了足够广的输入、领域分类、分析骨架、技术判断和证据材料，但这些成果尚未被充分转化为一套真正面向人阅读的最终报告。

必须明确区分以下四个层级：

| 层级 | v09 当前状态 |
|---|---|
| 原始输入与证据 | 很完整 |
| 分类、聚类和分析骨架 | 已形成 |
| 专家内部研究稿 | 内容丰富 |
| 面向人的最终技术综述 | **尚未真正完成** |

因此，不能再用“某个问题在材料中出现过”“每个 cluster 都有对应章节”来证明输出已经完成。用户验收的对象是最终阅读体验和认知价值，而不是研究账本的字段覆盖率。

## 二、确认的问题

### 1. 报告入口从研究过程开始，而不是从领域答案开始

字段树、架构报告和专题报告经常先展示 entity 数、mapping 数、窗口、cluster ID、primary/secondary membership 和内部审计口径。

这些信息适合方法附录，不适合成为普通读者理解 Agent Memory 的入口。读者首先需要得到的应是：

- Agent 为什么需要 Memory；
- 当前 Memory 主要在解决哪些问题；
- 整体技术路线和通用架构模型是什么；
- 最近发生了哪些重要变化；
- 哪些部分相对成熟，哪些仍处于研究阶段。

### 2. 内部研究语言泄漏到读者正文

正文中存在大量内部 claim/evidence ID、packet ID、cluster ID、saturation 记录和审计表达，例如：

```text
FND-C17/FND-EV32–33
REP-C02/REP-V03–04
OPS-C07/OPS-J07
mapped/deep-verified
actual saturation cycles
```

这些信息对可追溯性有价值，但不应占据读者的注意力。读者正文应该使用自然语言、论文或项目名称，以及简洁可点击的引用。内部编号和完整审计关系应进入脚注、悬浮信息或独立附录。

### 3. 术语密度过高，缺少由直观解释到专业定义的过渡

当前文字经常直接使用混合中英文的高密度术语，例如 typed/provenanced state、mutation plane、context compiler、action-time authorization、bounded abstention 等。

这些术语可以保留，但应遵循：

```text
实际问题或场景
→ 通俗解释
→ 技术机制
→ 精确定义
```

不能默认读者已经理解整套内部分类和架构。

### 4. 文件很多，但跨文件综合工作仍被留给读者

当前信息分散在字段树、架构全景、执行结论、共识报告、14 个 cluster、16 个 project、benchmark、安全、标准和采用报告中。

读者仍需要自己完成以下连接：

```text
问题是什么
→ 为什么简单方法不够
→ 当前有哪些方案
→ 方案怎样运行
→ 各方案适合什么条件
→ 有哪些论文和工程实现
→ 哪些结论已经验证
→ 还有什么没有解决
```

这本应由最终报告作者完成，而不是要求读者阅读 45 个文件后自行拼装。

### 5. Cluster 报告形式完整，但模板和验收表痕迹过重

大多数 cluster 报告形式上已经覆盖问题、架构、数据流、成本、benchmark、失败和缺口，但统一模板非常明显。

“实际饱和轮次”“补充可审计工程判断”“分层证据选择”等内容大量进入正文，使报告更像研究验收材料，而不像有自然叙事的技术专题。不同 cluster 的真正重点不同，不应为了结构对称而强制使用同样的篇章权重。

### 6. 方案已经被发现，但尚未稳定整理成面向读者的方案谱系

当前报告提到了许多机制和项目，但解决方案经常埋在连续段落中。每个重要分支都应形成清晰的方案家族比较，例如：

| 方案路线 | 如何工作 | 解决什么问题 | 优势 | 代价与失败模式 | 代表论文/仓库 | 成熟度 |
|---|---|---|---|---|---|---|
| Flat/vector retrieval | 按语义相似度召回 | 表述不同的历史事实 | 简单、低成本 | 时间、关系和冲突较弱 | 代表实现 | 工程常见 |
| Hybrid retrieval | 结合向量、关键词和过滤 | 精确事实与语义召回兼顾 | 稳健 | 调参与组合复杂 | 代表实现 | 较成熟 |
| Graph navigation | 沿实体与关系搜索 | 多跳和关系问题 | 结构可解释 | 建图和维护成本高 | 代表实现 | 条件成熟 |
| Temporal/versioned retrieval | 先解析时间和版本 | 新旧事实与 as-of 问题 | 能处理历史与冲突 | 状态模型复杂 | 代表实现 | 早期至中期 |

读者需要看到经过综合的方案空间，而不是自己从论文和项目段落中归纳。

### 7. 未解决问题仍以研究审计语言为主

例如“缺少跨 backend、同任务流、同预算的独立复现”是正确的研究判断，但面向读者还需要解释其实际含义：

> 目前无法可靠判断：把系统从简单向量检索升级为完整生命周期控制后，究竟能提升多少效果、增加多少成本。已有实验使用的模型、数据、后端和预算不同，不能直接比较。

每个缺口都应回答：

- 我们目前不知道什么；
- 为什么不知道；
- 这会影响哪个工程或产品决策；
- 需要什么实验或证据才能解决。

### 8. “已有内容”不能替代“可读成品”

过去的判断错误在于：看到字段树、架构段落、方案名称和 gaps 后，就认定“问题、方案和未解问题已经写好了”。

新的验收标准是：

> 一位没有参与研究流程的技术读者，能否不理解内部 schema 和 ID，也不需要自行跨文件综合，就准确回答该领域在做什么、如何做、不同方案有何差异和适用条件、哪些问题仍未解决。

## 三、下一版必须新增的读者成品

### 1. 一份真正的总报告

总报告应成为默认入口，并至少包含：

1. Agent 为什么需要 Memory；
2. Memory 保存哪些不同类型的状态；
3. 当前领域主要解决哪些问题；
4. 一张直观的领域全景图；
5. 一套描述性的通用架构模型或架构解剖图；
6. 各技术分支及其相互关系；
7. 每个分支的主要方案家族；
8. 最近 12 个月和 90 天发生了什么变化；
9. 当前共识、争议和成熟度；
10. 不同应用场景如何组合、替换或省略各模块；
11. 重要的未解决问题、证据现状与不确定性。

总报告必须可以独立阅读。其他文件用于展开深度，而不能用于补齐总报告缺失的基本逻辑。

### 2. 一张真正面向读者的大图

大图至少同时表达：

```text
现实问题
→ Memory 保存的对象
→ 写入/管理/读取/行动链路
→ 对应技术分支
→ 主要方案路线
→ 安全、评测与成本横切面
```

它不是 corpus DAG、cluster ID 图或内部 taxonomy 可视化，而是一张让读者在数分钟内建立整体心智模型的图。

### 3. 每个重要分支的读者版专题

每份专题应自然回答：

1. 用一个具体场景说明问题；
2. 为什么简单方法不够；
3. 当前有哪些方案家族；
4. 每种方案如何运行；
5. 架构、算法和数据流；
6. 重要论文、GitHub 实现及其候选理由；
7. 方案的横向比较与适用条件；
8. 当前共识和反方证据；
9. 主要失败模式；
10. 尚未解决的问题；
11. 对该方向成熟度、代价和证据强弱的暂定判断。

不同分支可以采用不同的篇章结构和篇幅，不必继续为了 schema 对称而套用完全一致的模板。

### 4. Project 报告必须以项目自身为中心

项目报告应突出：

- 它属于哪条技术路线；
- 与同类方案相比最大的不同；
- 核心组件和数据流；
- 实际依赖、存储、索引和接口；
- 如何接入现有 Agent；
- 适合和不适合什么场景；
- 项目特有的失败模式和维护边界；
- 哪些是代码中可见的事实，哪些只是项目方声明，哪些仍未验证。

不能让 16 份项目报告看起来只是同一工程检查模板替换了仓库名称。

### 5. 审计材料与读者材料分层

建议明确分为：

```text
reader/
  overview.md
  architecture.md
  solution-landscape.md
  trends.md
  clusters/*.md
  projects/*.md

audit/
  sources.jsonl
  claims.jsonl
  evidence.jsonl
  semantic_checks.jsonl
  screening.jsonl
  saturation_events.jsonl
```

读者可以从正文进入证据，但不应被内部研究流程和账本结构打断。

## 四、读者版验收标准

下一版输出只有同时满足以下条件，才能称为面向人的最终报告：

1. **五分钟总览：** 新读者只读默认入口，就能说清 Memory 在解决什么、整体架构是什么、主要路线有哪些。
2. **专题自包含：** 每个重要 cluster 不依赖其他报告，即可回答“问题、方案、原理、比较、未解问题”。
3. **方案优先：** 正文按问题和方案组织，论文与仓库作为证据和实例出现，而不是成为篇章骨架。
4. **自然语言优先：** 正文不要求读者理解内部 ID、schema、mapping 或 saturation 术语。
5. **比较明确：** 每个重要分支至少有一张方案横向比较或等价的清晰综合。
6. **证据不抢叙事：** 引用可追溯，但内部 claim/evidence ID 不主导阅读体验。
7. **缺口说清楚：** 每个关键未解问题都说明目前不知道什么、为什么不知道、会影响哪些判断以及证据还缺在哪里。
8. **按重要性分配篇幅：** 不为模板一致而平均分配篇幅；重要、最新、争议大或工程价值高的方向应更深入。
9. **无需阅读全部文件：** 读者不必先读完 45 个文件，才能理解报告的总体结论。
10. **独立读者测试：** 应由未参与研究过程的人试读，检查其能否复述领域结构、核心方案和主要不确定性。

## 五、对 v09 的最终定位

v09 应被定位为：

> 一套广度充足、分析骨架完整、证据和内部研究材料丰富的高质量研究底稿。

但它目前不应被定位为：

> 已经完成编辑、叙事、解释和视觉组织的最终读者版技术综述。

下一轮的首要任务不是继续扩大输入，也不是增加更多审计字段，而是完成最后一层转化：

```text
内部研究材料
→ 跨分支综合
→ 读者心智模型
→ 自然叙事
→ 方案比较
→ 描述性判断
→ 审计材料下沉
```

除非新的写作过程发现实质证据缺口，否则不应再用扩大检索或增加账本复杂度替代这项编辑与综合工作。

## 六、经 Grill 确认的 v10 输出契约

以下内容是 2026-08-12 后续 Grill 的最终确认结果。它覆盖本文件前文中与之冲突的早期建议，并作为通用 `track-tech-frontier` Skill 与 Agent Memory v10 的输出目标。

### 1. 目标读者与报告职责

核心读者是了解 Agent/LLM 基础、但并非 Agent Memory 专家的技术负责人或架构师。报告的目标是帮助读者建立领域心智模型、理解不同路线的机制与状态，而不是替读者完成技术选型。

主报告必须是一张可以独立阅读的完整大地图。读者看完后，应能大致说明：

- Agent Memory 整体在解决什么问题；
- 一个 Memory 系统通常如何运转；
- 当前主流方向之间是什么关系；
- 近一年和近 90 天出现了哪些实质变化；
- 各方向的成熟度、代价、失败模式、共识和争议是什么。

主报告不承担所有技术细节。特别深入的机制、算法、工程实现和证据应下沉到分支报告与项目报告。

### 2. 三层读者结构

读者版采用三层结构：

```text
技术机制主分支
→ 应用场景跨分支视图
→ 重点 GitHub 仓库工程案例
```

技术机制是主要深挖单元，至少围绕下列链路组织，但不预先锁死分支数量或名称：

```text
记忆对象与作用域
→ 写入、抽取与记忆形成
→ 表示、存储与索引
→ 更新、巩固、冲突处理与遗忘
→ 检索、排序与上下文构造
→ 使用、反馈与经验/技能学习
```

评测与 Benchmark、安全与隐私、权限与治理、成本与可靠性、可观测性、互操作与工程集成作为横切问题。

应用场景用于解释各技术分支如何组合或裁剪，例如个人助手、Coding Agent、多 Agent、世界状态、具身和多模态记忆。场景视图不重复基础机制，也不转化为推荐方案。只有形成独立技术路线的场景，才升级为技术主分支。

新的读者分支可以重命名、合并或拆分现有 v09 cluster，但必须保留到旧分类和原始证据的映射。

### 3. 通用架构模型，而非推荐架构

主报告提供一张描述性的“通用架构模型”或“架构解剖图”，说明主流系统通常包含哪些模块、数据如何流动、不同路线会替换或省略哪些模块，以及横切问题如何作用于各层。

这张图可以展示多种架构变体，但不得：

- 宣称存在行业唯一标准架构；
- 标注推荐路线或默认组合；
- 给出统一最佳方案、排行榜或技术选型结论；
- 提供上线方案或最小验证清单。

报告仍应提供描述性分析，包括适用条件、成立前提、成熟度、代价、失败模式、共识、争议和弱信号；这些属于技术理解，而不是替读者作选择。

### 4. 分支报告必须先综合，再深挖

每个重要分支在没有人工介入时也必须是一份完整成品，并至少回答：

- 该方向解决什么问题，边界是什么；
- 当前有哪些主要方案族；
- 各方案的架构、算法、数据流和工程实现有何差异；
- 当前主流做法、近期变化和新出现的弱信号是什么；
- 有哪些重要论文、仓库、Benchmark 和负面证据；
- 已形成哪些共识，哪些仍有争议；
- 主要代价、失败模式和未解决问题是什么；
- Skill 对成熟度和证据强弱的暂定判断是什么。

组织方式必须是“问题与方案优先”，不能按论文或仓库逐项写简介。先对方案空间做较大规模的整理、聚类与比较，再选择少量有信息增益的材料深入分析。深挖对象通常覆盖当前主流、最新路线、真实工程实现和关键反例，但不设置统一的论文数、仓库数或篇幅门槛。

对于“最具代表性的论文或仓库”“最重要的未解决问题”等主观性很强的判断，Skill 应先给出完整候选、分类、暂定判断和理由。容易判断的可以直接陈述；困难或分歧较大的进入人工评审清单，不伪装成确定结论。

### 5. GitHub 的两层输出

GitHub 内容采用：

```text
广泛候选雷达
→ 少量重点项目工程报告
```

候选雷达保证广度和新近性；项目报告负责回答代码实际上如何工作。重点项目报告至少应分析：

- 它实现了通用架构模型中的哪些环节；
- 核心组件及组件关系；
- 写入、存储、索引、检索、更新和使用的数据流；
- 实际依赖、存储、外部服务与接口；
- 集成方式、部署约束和扩展边界；
- 维护、测试和版本状态；
- 项目特有的失败模式与未验证风险；
- 哪些能力可由代码或固定文档确认，哪些只是项目方声明。

不得按 Star 或固定数量机械选择项目，也不得再批量生成换名式仓库简介。Star 只用于发现候选和反映单点关注度，不能单独证明质量、增长趋势或生产采用。

### 6. 时间重点与研究边界

下一版重点覆盖：

- 当前主流路线；
- 最近 12 个月的实质进展；
- 最近 90 天值得关注的新论文、新项目和弱信号。

不设置“奠基工作”固定章节，也不为了历史完整性收录旧工作。旧工作仅在不解释它就无法理解当前路线时简短回溯。“最新”不自动等于“重要”；证据不足的新项目进入弱信号层，不能直接升级为主流结论。

长上下文、普通 RAG、模型参数记忆、持续学习、Checkpoint 和工作流状态等相邻技术只作边界或替代方案略写，不作为主体分支。只有当它们承担跨会话记忆、写入管理、检索使用或持续演化职责时，才进入 Agent Memory 主体分析。

### 7. 输入策略与质量核验

v10 复用 v09 已有的广泛语料，不重新从零进行同规模全量发现。先重构读者分支，再针对各分支缺失的机制、架构、实现、近期项目、负面证据和公平比较做定向补查。

采用分层核验：

- 核心结论、关键数字、版本状态、方案比较、安全与采用事实必须有可靠证据；
- 一般性架构解释不强制拆成逐句 claim，只需来源合理、逻辑自洽；
- GitHub 默认进行代码、目录、依赖和文档层面的工程分析；只有运行结果会改变核心结论时才执行仓库；
- 不为证明绝对无遗漏而无限搜索；主要方案空间已经覆盖、继续检索不再产生一级方向时即可收束；
- 审计账本继续保留，但不得主导读者叙事，也不得因非关键字段缺失阻止成品交付。

### 8. 人工评审是可选升级，不是报告前置条件

评审前的主报告、分支报告和项目报告必须已经完整、自洽、可独立阅读。人工评审清单只收录少量高影响、高不确定性事项，例如：

- 证据冲突且可能改变领域判断；
- 新趋势信号强，但尚未形成稳定结论；
- 多个候选都合理，无法客观确定代表性；
- 是否继续深挖取决于用户关注的场景；
- Skill 的暂定判断置信度较低。

人工只需决定是否改判、调整重点，或触发某个分支、论文、仓库和问题的增量深挖。没有被人工评审的方向继续使用完整首版结论，不要求逐方向审批。

### 9. 完成与验收标准

最终验收以读者理解和分析深度为准，而不是文件数、论文数、仓库数、claim 数或验证器全绿。完成至少意味着：

- 新读者只看默认入口，就能复述领域问题、通用架构模型、主要方向及其关系；
- 不打开证据账本，也能理解当前主流和近期变化；
- 任意重要分支都能独立呈现方案空间、关键机制、工程实现、比较、失败模式和暂定判断；
- 重点项目报告能够说明代码真实结构与可借鉴部分，而不是复述 README；
- 近期论文和仓库被放回相应技术脉络，而不是堆进孤立的“最新动态”附录；
- 正文没有等待人工补全的空洞章节；
- 抽查关键事实可追溯，但普通读者不需要理解内部 schema、ID 和审计流程。

### 10. 版本与通用化

本契约同时作用于两项后续工作：

1. 升级通用 `track-tech-frontier` Skill，使以后调研其他技术时也遵循上述读者输出结构；
2. 以 Agent Memory v10 作为新版 Skill 的参考实现和验收样例。

v09 作为已有研究快照完整保留，不覆盖、不伪装成 v10。人工评审后的变化以增量版本记录，并说明触发原因与判断变化。

### 11. v10 分支深度复盘与新增硬约束

v10 第一版解决了总览和读者入口问题，但六个机制分支仍然过度压缩：通常只有一张方案表，再用一两段概述带过每个方案。这样的页面可以告诉读者“有哪些名词”，却不能让读者理解“大家具体怎么做”以及“最新研究究竟在推进什么”。

因此，后续分支报告不得把以下内容视为深度分析的替代品：

- 一张列出方案名称、优缺点和成熟度的总表；
- 每篇论文或每个仓库各写几句简介；
- 只画通用数据流，而不解释各方案如何实现其中的步骤；
- 用“近期活跃”“研究仍早期”等概括替代具体研究问题；
- 把完整细节留在旧审计报告，读者版只保留摘要。

每个主要方案族都应被真正打开，至少说明：

1. 它保存或操作的状态结构是什么；
2. 写入、管理、读取和使用链路中实际执行哪些步骤；
3. 关键算法、规则、控制决策或一致性语义是什么；
4. 代表论文和仓库分别实现了哪一种具体形状；
5. 它在什么条件下成立，成本转移到哪里，会怎样失败；
6. 最近 12 个月和 90 天的工作正在修改哪一层，而不只是出现了哪些新名称；
7. 当前尚缺哪种机制、实现或实验，为什么这使结论无法继续推进。

分支完成后的读者验收问题是：

> 一个了解 Agent/LLM、但没读过这些论文的读者，能否仅凭该分支报告，复述至少几类主要方案的内部工作方式、代表实现之间的实质差异，以及当前研究正在解决的下一批问题？

如果只能复述方案名称和优缺点，该分支仍是扩展提纲，不是技术深潜。篇幅不设统一配额，但任何重要方案族只有几句话、没有算法/数据流/工程实现和近期研究议程时，应直接判为未完成。
