# Agent Memory HTML 写作规范

## 适用范围

本规范只适用于 `frontier-research/agent-memory-practical/site` 及其 `2026-08-25/reader` Markdown 来源。它不是 `track-tech-frontier` 的通用写作规则，也不约束其他调研套件。

## 核心原则

每一层不套固定页面模板。先判断观众在这一层真正需要理解什么，再决定通用抽象、案例、图片和篇幅。

- 如果跨项目存在一个真正有解释力的通用架构或概念，先抽象出来讲清楚。
- 接下来只选择能把该层机制讲具体的案例。案例可以来自 TencentDB、Codex 或前沿探索，不要求每个来源都出现，也不按来源凑数。
- 案例尽量使用许可清楚、适合讲解的论文原图或项目图；没有合适原图时，再制作来源约束的自绘图。
- 正文负责带观众读图：从哪里开始、发生什么、得到什么，以及这张图为什么能说明本层机制。不要在图旁重复项目简介或整篇论文摘要。
- 案例段落直接说明该案例实际怎样工作。不要主动添加“这是该系统特有”“不代表所有系统都有”一类防御性免责声明；只有跨系统比较本身是当前讲解问题时才讨论共性或差异。
- 用户用“不要怎么做”或“不是什么”来纠正编辑方向时，默认应把约束静默落实为正确结果，不把纠正过程、排除项、范围声明或免责声明转写给观众。例如，用户要求某个机制不要被泛化，就只在正确范围内讲该机制，不额外解释“它并不通用”；用户要求删除某项内容，就直接删除，不向观众说明为何未收录。
- 不要机械地按否定句式处理。若用户明确要求观众理解某个否定判断，或者该判断本身是定义概念不可缺少的内容，则可以写入正文。应根据用户意图判断这句话是在约束编辑行为，还是在指定观众内容。
- 研究过程、固定提交细节、JSON/JSONL、内部字段、审计语言和下一层机制，除非理解当前页面不可缺少，否则不进入观众页面。
- 通用概念和有价值的案例讲清以后，页面立即结束；不要追加总结套话、讲解提示或阅读路径。

这套原则不意味着每层必须具有“通用图 + 两个案例”的相同结构。不同层可以没有通用图、只有一个案例，或者需要多个互补案例。

## 已确认页面边界

### 总览与架构

只包含：Agent Memory 是什么、六层架构图、为什么选 TencentDB 和 Codex、两个案例的简短介绍。页面结束在 Codex Local Memory 的介绍，不追加比较总结。

### 第 1 层：输入

只解释输入形式和上下文封装，然后保留 WorldLines 的世界/设备状态案例。视觉观察只作为通用输入类型出现在总图和正文中，不展开 XSkill。删除 TencentDB/Codex 工程展开、JSON/JSONL、形成阶段内容和 Computer Use。

### 第 2 层：提炼与管理

通用主线只说明输入经过筛选、抽取和去重后，与已有 Memory 比较并产生 create、update、merge 或 no-op。其他管理机制作为案例特有补充，不强行串成一条统一流水线。

案例顺序固定为：TencentDB 完整 L0 → L1 → L2 → L3、TencentDB Skill、Wiki/代码仓库简述、Codex 两阶段提炼与文件级管理、前沿来源校验和遗忘。通用概念中的术语必须能在后续案例中大致对应，但观众页面不展示逐项证据审计。

旧第四层“管理与演化”不再发布；其仍有价值的更新、删除、遗忘内容迁入第二层。原 Markdown 暂时作为迁移底稿保留，不作为站点页面。

### 第 4 层：反馈与持续学习

先讲“Memory 被使用 → 得到任务结果 → 归因与评估 → 更新学习对象 → 改变下一次行动”的通用闭环。TencentDB 与 Codex 只承接前文，分别说明轨迹驱动的 Skill 版本更新与 citation 驱动的来源选择，不重复第二层的形成细节。

前沿案例只保留三个互补机制：XSkill 说明结果怎样更新 Experience 与 Skill 内容，CoEvoSkills 说明验证反馈怎样推动 Skill 与验证方法共同演化，MemCon 说明任务结果怎样更新 Memory 操作策略。每个案例使用论文主图，正文即使脱离图中小字也要能够讲清输入、反馈、更新对象和下一次行为变化。页面在 MemCon 机制与作用讲清后结束，不追加基准列表或总结性项目盘点。
