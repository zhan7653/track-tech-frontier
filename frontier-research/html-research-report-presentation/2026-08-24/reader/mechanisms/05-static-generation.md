# 静态生成、兼容与扩展边界

## 问题与边界

当前仓库强调 Python 标准库、UTF-8、相对链接和确定性验证。展示层必须延续这些性质，不能要求研究作者改用另一套工作流。

## 方案家族

### 外部出版工具适配

直接调用 Pandoc/Quarto/MkDocs 能获得成熟语法与主题，但安装、版本和插件成为构建输入。适合可选适配器，不适合默认路径。

### 引入 Markdown 库

Python Markdown、markdown-it 或 remark 比自写解析器兼容更广，代价是依赖和安全配置。若未来语法明显超出当前子集，应优先选择并固定一个解析库，而不是无限扩展自写实现。

### 受限标准库解析器

针对当前 GFM 子集实现 headings、paragraphs、lists、tables、links、code、blockquote、Mermaid。优点是零安装和可审计；必须对不支持语法告警，不能自称完整 Markdown。

### 浏览器运行时 Markdown

把源文本交给 JS 渲染会简化构建，却让首屏、搜索、打印和安全依赖运行时，不适合作为默认。

## 生成协议

输入页被转换为语义节点；链接先解析到源路径，再重写为输出路径；所有输出写入新目录，不覆盖 Markdown。`build-manifest.json` 记录输入/输出 SHA-256。生成器提供 `--check` 或验证命令检查断链、标题、编码、危险 URL 和清单一致性。

## 成本与失败

- 标准库解析器最危险的失败是“看起来能用但悄悄改变语义”。
- 直接复制本地绝对路径会让站点不可移植。
- 共享资源路径在嵌套页面中容易计算错误。
- 输出目录位于输入树中时，发现过程必须排除自身，避免递归生成。

## 当前研究议程

当前 56 页只使用 text/json/mermaid 围栏、42 个表格文件和少量 blockquote，没有脚注、图片或原始 HTML。这个可观测子集足以支持第一版，但实现必须把兼容矩阵写入 README，并用真实套件回归。
