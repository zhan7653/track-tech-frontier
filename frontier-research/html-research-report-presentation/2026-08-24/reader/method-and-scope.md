# 方法与范围

## 研究合同

读者是对报告主题有一般技术背景、但第一次进入该专门领域的人。研究对象是开源仓库、公开 Skill 和权威 Web 规范中可被本仓库吸收的展示机制；不比较商业托管体验，不推荐通用建站赢家。

## 检索路线

先以“scientific publishing / technical documentation / interactive article / research agent report / agent skill / accessibility”多路试探，再按六个机制分支补查。GitHub API 用于固定仓库身份、默认提交和当前元数据；关键结论回到固定提交的文档/代码或官方说明。两篇论文分别补足作者界面与交互边界，W3C 补足结构化可访问性。

## 三类语料

- **发现：** 22 个候选，用于防止只盯某一框架。
- **映射：** 对能改变机制图或边界的项目确认身份和角色。
- **深验证：** 打开固定版本的关键代码/文档，支持读者结论；未运行外部项目。

## 停止依据

最后两轮分别针对“中文离线搜索/无脚本退化”和“重型框架能否被轻量组合替代”。它们没有新增一级机制，只细化了构建时索引、文本后备和安全边界。剩余问题被保留在开放问题中。

## 限制

- 没有开展用户研究或可用性实验；实现验收只能证明可操作与布局质量，不能证明学习增益。
- GitHub 元数据是 2026-08-24 的单次观察，不能用于增长判断。
- ReActicle、`beautiful-article`、`tech-route-maker` 等近期项目只作为弱信号。
- 本次不测试公式、复杂脚注、嵌套 HTML 和任意 Mermaid 语法；实现必须对超出边界的输入明确退化。
