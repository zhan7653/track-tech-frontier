# Coding Agent：项目不是一段更长的聊天记录

Coding Agent 的跨会话 Memory 面对的是持续变化的软件项目。它既要记住代码结构和任务历史，又不能把已经变更的分支、过期的失败结论或含密钥的终端输出当成当前事实。这里的核心对象不是“开发者偏好”，而是带仓库、工作树、提交和权限边界的项目状态。

## 这个场景保存什么

一个项目通常同时需要四类记忆：代码符号、调用和依赖关系；issue、尝试、修复与设计决定；仓库特有的工作规则；以及从测试、评审和任务结果得到的反馈。Git 对象、当前文件和测试结果仍是外部真值；Memory 保存的是帮助定位、解释和避免重复工作的派生状态与判断历史。

| 对象 | 何时写入 | 怎样读取/使用 | 为什么不能用普通聊天摘要替代 |
|---|---|---|---|
| 代码结构 | 提交或工作树变化后建立/更新索引 | 为定位、影响分析和上下文拼装提供候选 | 必须知道对应哪个提交与文件版本 |
| 开发事件与判断 | issue、工具结果、尝试、修复或人工决定发生时 | 回答“试过什么、为何失败”，并在行动前提示风险 | 需要可追溯、可被新证据推翻 |
| 仓库规则 | 人工维护或从项目文档抽取 | 只在相关任务注入 | 静态文本可能增加成本而不改善完成率 |
| 反馈与策略 | 测试、评审、修复结果回流后 | 调整排序、阻断已知危险动作或在影子模式学习 | 反馈不等于可安全推广的通用规则 |

## 场景组合：版本化的 write → manage → read → use

```text
代码 / Git / issue / 工具与测试回执
                 │
                 ├─ 权威事实：当前 worktree、commit、权限、测试结果
                 ├─ 项目事件账本：尝试、决定、失败原因、修复
                 ├─ 可重建投影：符号/依赖图、语义索引、摘要
                 └─ 反馈与策略状态：排序、审查、回滚线索
                                      │
任务 + repo/branch/worktree/commit ───> 版本过滤与定位
                                      │
                           最小上下文 + 行动前复核 ──> 编辑/命令/工具
                                      │
                                 新提交、测试和失败回写
```

同一条“这个文件很脆弱”的记忆，必须说明它基于哪个版本、是否已被后续重构推翻。索引与摘要是为读取服务的投影，不能反过来覆盖当前代码事实；行动前还要重新检查工作树、权限和测试条件。这种组合把写入、索引、检索、上下文编译和使用拆开，才能区分“找到了相关文件”和“做出了正确修改”。

## 主流方案形状与实际工程

| 形状 | 如何工作 | 代表材料 | 约束与失败面 |
|---|---|---|---|
| 结构化代码索引 | 将符号、依赖或代码图作为可查询的项目表示 | [Code Isn't Memory](https://arxiv.org/abs/2606.22417)；[Engraphis](https://github.com/Coding-Dev-Tools/engraphis) | 索引必须与提交对齐；嵌入模型变化可能要求重建 |
| 事件溯源项目记忆 | 记录 issue、尝试、修复与决定，再投影为摘要和行动前提示 | [PROJECTMEM](https://arxiv.org/abs/2606.12329) | 事件可能陈旧或泄露敏感输出；摘要不能取代 Git/测试真值 |
| 被动仓库上下文 | 将 AGENTS.md、说明或规则文件直接注入会话 | [Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988) | 上下文变长不等于更会做任务，可能提高推理成本 |
| 反馈条件策略 | 保留检索与修复结果，以确定性排序为主、学习策略为受限增量 | [Feedback-Normalized Developer Memory](https://arxiv.org/abs/2605.01567) | 反馈偏差、错误泛化和未验证的在线策略风险更高 |

结构索引的作者实验固定模型并比较 index-on、index-off 与 agentic-grep；在其给定的 SWE 任务协议中，索引开启的 resolve 为 50.4%，关闭为 41.9%，agent-targeted localization@5 为 84.5% 对 44.3%，而每单元平均成本为 1.15 美元对 1.19 美元。这是一个受模型、样本、检索器与实验脚手架限定的作者结果，而非“所有 Coding Agent 都应保存全库索引”的结论。[研究论文](https://arxiv.org/abs/2606.22417)

反过来，AGENTS.md 研究报告：在其测试的多种代理、模型及自动/人工维护的上下文文件中，仓库级上下文通常没有普遍改善任务成功，平均推理成本增加超过 20%。这并不否定项目记忆；它区分了按版本、任务和行动点检索的结构化状态，与无差别注入更多文本。[研究论文](https://arxiv.org/abs/2602.11988)

在工程层，Engraphis 的固定提交将 CLI、MCP、REST 与面板接到同一 MemoryService；SQLite 保存记录、全文检索、双时间历史、图与代码链接，查询再融合词法、向量、图和代码信号并按预算打包。它也明确暴露了嵌入指纹不一致时禁用持久向量检索、以及 sqlite-vec 与 SQLCipher 的原生库冲突等约束。[v09 固定提交工程报告](../../../agent-memory-v09/bundle/projects/coding-dev-tools-engraphis.md)

## 近期变化与开放问题

近一年的变化是项目状态越来越从“说明文件”转为可更新的结构索引、事件账本和受反馈约束的策略；近 90 天的新工程项目也更常通过 MCP 暴露检索与写入。但这是一种工程供给信号，不等于性能或生产采用已经收敛。

2026-08-23 对 [`openai/codex`](https://github.com/openai/codex) 的固定版本检查补充了一种此前没有进入 v09 深潜的现役 Coding Agent 形状：它从近期 idle root threads 中做逐 rollout 抽取，再启动受限内部 Agent 把候选巩固为全局 `MEMORY.md`、prompt-resident `memory_summary.md` 和按需展开的 rollout summaries/skills；读取端没有向量检索，而是 Agent 根据常驻摘要做词法搜索和渐进披露。它同时暴露了全局物理 store 与 cwd/branch 逻辑 scope、使用次数驱动保留、subagent 不独立生成 Memory、以及 item-level delete/跨项目隔离仍较弱等边界。完整代码级分析见 [Codex 本地 Memory 系统](../projects/openai--codex.md)。

仍没有一个公开协议能在相同仓库、任务、模型、预算和回放条件下公平比较代码图、事件账本、静态上下文和反馈策略。并发工作树、索引失效、机密捕获、删除派生索引、以及“检索到了正确前例却仍修改错误”的行动失配，也缺少共同的端到端证据。因而这个场景的成熟度不是一个分数：底层索引和日志很常见，跨版本治理与可验证的反馈学习仍较早期。

相关机制可继续阅读：表示/索引、生命周期、检索与上下文构造、经验与技能，以及安全和可观测性专题。本页只说明它们围绕项目版本和开发行动如何组合。
