# 共识、分歧与开放问题

## 相对稳固的共识

- 长技术报告需要稳定标题层级、套件导航和页内位置感。
- Markdown 与语义化中间表示比自由手写 HTML 更适合可重建输出。
- 图、表、引用、代码和 callout 应是内容类型，不只是视觉样式。
- 关键内容不能只存在于 hover、折叠区、canvas 或运行时数据里。
- 构建时检索和静态输出能降低服务依赖，但索引范围必须公开。
- 自动生成内容进入 HTML 前必须转义或净化。

## 主要分歧

### 单文件还是多页站点

单文件最容易分享和归档；多页站点更适合 56 个页面的独立链接、增量构建和清晰 URL。本仓库更接近后者，但应允许导出一个入口压缩包，而不是把所有正文重复嵌入一个 HTML。

### 通用 Markdown 还是扩展语法

Quarto/MyST 的扩展能准确表达图、引用和组件，却要求作者学习新语法。当前实现应先完整支持现有 GFM 子集，再把 callout 或概念卡作为可选约定。

### 构建时 SVG 还是浏览器 Mermaid

构建时 SVG 离线、可打印、可索引；浏览器 Mermaid 更兼容完整语法。第一版可以支持仓库已有的 flowchart 子集并保留源代码，未来再接可选 Mermaid CLI。

## 尚未解决的问题

1. 内置 Mermaid 子集如何明确报出不支持语法，而不悄悄画错？
2. 中文搜索是否需要分词，还是标题/章节/Unicode 子串已经覆盖当前规模？
3. 怎样在不把 audit ID 暴露给普通读者的前提下，让外部来源就近可检查？
4. 是否需要单文件归档模式；若需要，搜索索引与 56 页正文应怎样避免体积膨胀？
5. 未来报告出现公式、脚注、图片和复杂嵌套列表时，标准库解析器的边界在哪里？

这些问题不阻止第一版：都可以通过明确告警、文本后备和可选适配器保持可逆。
