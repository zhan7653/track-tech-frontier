# 相邻技术的边界：什么属于 Agent Memory，什么只是与它协作

Agent Memory 不是“任何能让模型带上过去信息的技术”的总称。本文采用一个描述性边界：当系统跨会话、跨任务或跨运行保存会影响后续行为的状态，并且需要处理写入、读取、更新、范围或演化中的至少一部分时，它进入 Agent Memory 主体。这个定义既包含外部数据库、文件、图和技能资产，也允许某些相邻技术在承担这些职责时成为主体的一部分。

反过来，某项技术只要主要解决当前窗口容量、静态知识查找、模型权重训练或一次任务的可恢复执行，而不负责这种持久状态的形成与使用，它就保持为相邻层。边界不是给技术排高低，而是避免把不同故障、不同证据和不同评测问题混成一个“记忆能力”。

| 相邻技术 | 通常解决什么 | 通常是否属于主体 | 何时跨入主体 |
|---|---|---|---|
| 长上下文与上下文压缩 | 在当前推理窗口容纳更多信息 | 否，通常是工作上下文层 | 被写成可长期复用、可更新并跨会话检索的状态 |
| 普通 RAG | 从相对静态的外部资料找证据 | 否，通常是知识访问层 | 管理 Agent 产生的状态，包含写入、版本、范围或遗忘 |
| 参数记忆与持续学习 | 把规律保存在模型权重中 | 否，通常是模型学习层 | 外部记忆控制器决定何时形成、调用或修订持久经验，且该职责成为分析对象 |
| Checkpoint 与工作流状态 | 让一次运行恢复、重试或编排 | 否，通常是执行恢复层 | 状态被抽象为长期可解释的事实、决策、项目/共享世界状态，并在后续任务中被检索和更正 |

## 长上下文与上下文压缩：它解决“现在能装下多少”，不自动解决“以后该记住什么”

长上下文让模型在当前调用中直接看到更多原始材料；上下文压缩则在模型前压缩工具输出、日志、代码或对话，以降低 token 成本并保留任务所需信息。两者常与 Agent Memory 同时出现，因为任何持久存储最终仍要把一部分内容编译回有限上下文。

但它们通常不是 Agent Memory 的同义词。长窗口可能完全不产生跨会话状态；压缩也可能只是一次调用的临时摘要。它们并没有天然处理事实后来被更正、不同用户的可见范围、删除是否传播，或未来任务怎样重新找到正确内容。v09 的工程雷达把 Headroom、Claude-Mem 与 LightMem 所在的上下文压缩路径视为长期事实记忆的相邻层，正是因为它们的重点在 context compilation，而非仅靠名称判断。[v09 GitHub 雷达的边界说明](../../agent-memory-v09/bundle/reports/06-github-trend-radar.md)

当压缩结果被持久保存，带有来源、时间或版本，并在未来任务被选择性取回和更新时，它已经同时承担 Agent Memory 的一部分职责。此时真正要讨论的不是“它是不是摘要”，而是摘要是否可追溯、能否被更正、是否会覆盖原始证据，以及读取器会不会把它误当作当前事实。LightMem 复现研究显示，构造后的摘要型 store 也未必优于原始历史，结果会受 retriever 与 token 预算影响。[Reproducing LightMem](https://arxiv.org/abs/2607.29104)

## 普通 RAG：它解决“从资料库找证据”，不自动形成 Agent 的经历

普通 RAG 的典型对象是相对稳定的文档、网页、手册或知识库。它主要处理切分、索引、检索和引用；资料由人或外部流程维护，系统可以完全不知道哪个 Agent 在什么任务中见过、做过或学到了什么。因此，静态企业文档库本身属于知识访问，不应被扩展成 Agent Memory 主分支。

边界在于状态是否会演化。若检索库开始保存 Agent 的观测、工具结果、用户更正、项目决策或失败经验，并且有写入资格、对象类型、版本、撤销或遗忘的语义，那么它不再只是普通 RAG 的语料库，而是在承担 Memory 的状态管理。双时间 memory store 的工作就是一个清晰例子：它不仅检索文本，也区分事实身份、有效时间与被系统记录的时间。[Graph-Native Bitemporal Memory Store](https://arxiv.org/abs/2607.26520)

这条边界也解释了为什么不能把“向量检索效果”当作整个 Memory 系统的能力指标：Agent Memory 还必须面对写入错误、冲突事实、读取范围、派生摘要和之后的行动，而静态 RAG 未必涉及这些变更责任。

## 参数记忆与持续学习：它改变模型本身，外部 Memory 改变可见的状态

模型权重会吸收训练或微调中的规律，这常被称作参数记忆；持续学习研究则关心模型怎样在新数据下继续更新而不遗忘旧能力。它们确实影响 Agent 是否“记得”，但通常不在本文的主体：权重内部的具体来源、版本、用户范围和删除传播难以按一次外部状态转移直接检查。

外部 Agent Memory 的主要问题则不同：一个事实或经验何时写入、属于谁、何时失效、被哪些索引和摘要派生、又在什么行动前被读取。它可以与参数学习协作，却不能用“模型已经训练过”代替这些可审计的状态职责。

边界会在两个方向变得模糊。一种情况是外部系统保存经验，并把它定期编译为提示、工具策略或训练样本；另一种情况是学习出的控制器决定检索、巩固、遗忘或不操作。MemCon 将这类操作视为在线 policy 的选择，说明持续学习思想正在进入管理层，但这并不等于整个模型参数更新已经成为 Agent Memory。[MemCon](https://arxiv.org/abs/2607.13591) 目前也没有足够的可比证据说明参数化路径与外部状态路径可用单一分数衡量。

## Checkpoint 与工作流状态：它保证“这次任务能续跑”，不自动保证“下次任务理解过去”

Checkpoint、任务队列、工作流变量、工具调用日志和执行快照通常记录一次运行到了哪里，以便重试、恢复、审计或协调。这是可靠 Agent 系统必需的执行状态，但它的生命周期往往绑定某次运行：状态可能在任务完成后过期，或只被编排器读取，而不会成为未来推理的语义上下文。

它进入 Agent Memory 主体的条件是，运行状态被提升为可跨任务使用的持久对象。例如，一个 Coding Agent 将构建失败、已验证的假设、分支/提交关系和未完成决策保存为带来源和时效的项目状态；之后另一个会话可按任务检索、修订并据此行动。此时问题已不只是恢复某个进程，而是如何避免陈旧分支、错误工作树、秘密持久化或冲突决策。v09 的技术全景将项目和环境状态列为独立的记忆对象，并指出这类对象需要 repo、branch、commit、决策状态与权限边界。[v09 技术全景](../../agent-memory-v09/bundle/reports/03-landscape-synthesis.md)

反过来，单纯保存调用栈、临时变量或可重放步骤，仍应留在 workflow/checkpoint 层。把它们叫作“memory”并不会自动获得版本、语义更正、跨主体访问控制或行为适配能力。STALE 的结果尤其提醒这一点：即使外部状态已更新，也不能据此推定 Agent 后续行为已经改用新状态。[STALE](https://arxiv.org/abs/2605.06527)

## 为什么保持边界很重要

这些层可以组合，但它们的失败模式并不相同：长上下文首先受容量和注意力限制；普通 RAG 首先受语料、检索和引用正确性限制；持续学习受训练数据、遗忘和权重版本限制；checkpoint 受恢复一致性和幂等性限制；Agent Memory 还要额外承担长期写入、冲突、访问范围、遗忘传播和未来行动的风险。

因此，本报告把相邻技术作为接口和替代解释来讨论，而不把它们扩大成同等主分支。只有当它们实际承担跨会话状态的写入管理、选择性取回或持续演化职责时，才应进入 Agent Memory 主体分析。这个划分用于解释系统职责和证据边界，不构成技术选择建议。
